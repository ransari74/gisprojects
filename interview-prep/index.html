Section 01 · Foundations

What happens when you load a page

One question — type a URL, press enter, what happens? — has been asked in interviews for twenty years, because a complete answer touches DNS, TCP, TLS, HTTP, load balancing, caching, databases, and rendering. Learn it once as a spine, and every later topic hangs off it.

  1. The browser parses the URL

    https://api.example.com:443/v1/users?id=42#top decomposes into scheme (https, which sets the default port and demands TLS), host, port, path, query string, and fragment. The fragment after # is never sent to the server — it's browser-only. That detail alone has decided interview questions about analytics.

  2. DNS resolves the hostname to an IP address

    The browser checks its own cache, then the OS cache, then asks the configured recursive resolver (your ISP's, or 8.8.8.8). If the resolver doesn't have it cached, it walks the hierarchy: root nameserver → .com TLD server → example.com's authoritative nameserver, which returns the record. Each answer carries a TTL that controls how long it may be cached.

    Why this matters in design: DNS is the first place you can do load balancing and failover — return different IPs to different regions (GeoDNS) or rotate records. And DNS TTL is why a failover isn't instant: clients keep the old IP until the TTL expires. Modern services use anycast instead — the same IP announced from many locations, and the network routes you to the nearest one.

  3. TCP connects: the three-way handshake

    Client sends SYN, server replies SYN-ACK, client sends ACK. That's one full round trip before any data moves — 1 ms inside a datacenter, 70 ms across a continent. This is why connection reuse (keep-alive, connection pools) matters so much, and why a service that opens a new connection per request is slow for reasons that have nothing to do with its code.

    TCP gives you ordered, reliable, congestion-controlled delivery. It costs you head-of-line blocking: one lost packet stalls everything behind it. UDP gives you none of the guarantees and none of the cost — which is why video calls, gaming, and DNS use it, and why they handle loss at the application layer instead.

  4. TLS negotiates encryption

    The client offers cipher suites; the server returns its certificate chain; the client validates it against trusted roots; both derive a shared symmetric key. TLS 1.3 does this in one round trip (1.2 needed two), and supports 0-RTT resumption for repeat visitors — at the cost of replay risk, which is why 0-RTT is only safe for idempotent requests.

    The design consequence: TLS termination usually happens at the load balancer or CDN edge, close to the user, so the expensive handshake crosses a short distance. Traffic inside the trust boundary may then be plaintext, or re-encrypted for zero-trust environments.

  5. The HTTP request travels to a load balancer

    The IP you resolved almost certainly belongs to a load balancer, not to a server. Two kinds, and knowing the difference is table stakes:

    • Layer 4 (transport) forwards TCP connections by IP and port. It cannot see the URL. Very fast, very dumb, and it can't retry a failed request because it doesn't know what a request is.
    • Layer 7 (application) terminates the connection and reads the HTTP request. It can route by path or header, retry idempotent requests, do TLS termination, compression, rate limiting, and sticky sessions. Slower per request, and vastly more useful.

    Algorithms it might use: round-robin, weighted round-robin, least-connections (usually the best default), consistent hashing on a key (for cache affinity), and power of two random choices — pick two backends at random and send to the less loaded one, which gets nearly the benefit of least-connections without global state.

    The load balancer also runs health checks, and this is where candidates get caught: a shallow check (does the port accept a connection?) will happily route traffic to a process whose database connection pool is exhausted. A deep check verifies dependencies, but then one slow database can mark your entire fleet unhealthy at once. The real answer is a shallow check for routing plus a separate deep check for alerting.

  6. A server handles the request

    The kernel accepts the connection, the application reads it off a socket, routes it to a handler, and the handler does work — usually meaning it calls other things: a cache, a database, two other services. Nearly all of the request's wall-clock time is spent waiting on those calls, not computing. That single fact is why concurrency models matter more than raw language speed for most web services.

  7. The response comes back, and caching decides how much of this ever happens again

    Cache-Control: max-age=3600 lets any cache reuse the response for an hour. ETag plus If-None-Match lets the client ask "has it changed?" and receive a 40-byte 304 Not Modified instead of the body. Cache-Control: no-store means never write it down; private means only the browser, not shared caches. Getting these headers right removes more load than most optimizations you can make in code.

How services talk to each other

REST
Resources as URLs, verbs as HTTP methods, JSON bodies. Universal, cacheable by every proxy on earth, easy to debug with curl. Costs: over-fetching, under-fetching, and the N+1 problem where a list view triggers a request per item.
gRPC
Binary protobuf over HTTP/2, with generated clients and a strict schema. Much smaller payloads and faster serialization, plus native streaming in both directions. The default for internal service-to-service traffic. Costs: not human-readable, needs a proxy for browsers, and schema evolution requires discipline.
GraphQL
The client specifies exactly the fields it needs in one round trip. Great for mobile clients and for many-shaped frontends. Costs: caching is hard (everything is a POST to one endpoint), and an unbounded query can be an accidental denial of service — you need depth limits and query cost analysis.
WebSocket / SSE
For server-initiated data. See §11 — the tradeoff is stateful connections, which change how you scale and deploy.
Message queue
Not a request/response protocol at all. Use when the caller shouldn't wait, when the work can be retried, or when several systems need the same event.

The operating system half

You need enough of this to reason about capacity and failure, not enough to write a kernel.

Processes, threads, and why the distinction costs money

A process is an isolated address space: its own memory, its own file descriptors. A thread lives inside a process and shares that memory with its siblings. Sharing is what makes threads cheap to communicate between and dangerous to get wrong — two threads touching the same variable without coordination is a data race, and data races produce bugs that appear once a week in production and never in tests.

A context switch — the kernel swapping one thread off a core for another — costs on the order of a microsecond, plus the cache pollution afterward, which often costs more. Thousands of threads means the machine spends its time switching rather than working. That is the whole reason for the next idea.

Blocking vs non-blocking I/O: the C10K problem

If each connection needs its own thread and each thread blocks while waiting for the network, then 10,000 concurrent connections needs 10,000 threads, and the machine dies of context switching. The fix is an event loop: a single thread asks the kernel (via epoll/kqueue/IOCP) "which of these 10,000 sockets are ready?", handles those, and goes back to waiting. One thread, tens of thousands of connections, as long as no handler ever blocks.

The interview-ready summary: I/O-bound work wants concurrency (many things in flight, mostly waiting); CPU-bound work wants parallelism (many cores actually computing). Confusing them produces both of the classic mistakes — an async web server that pins a core doing JSON parsing, and a thread pool sized for CPU count that spends its life waiting on a database.

Memory, and why "it fits in RAM" is a design decision

The hierarchy — registers, L1/L2/L3 cache, RAM, SSD, network, disk — spans about eight orders of magnitude in latency (§10). Two practical consequences: sequential access is dramatically faster than random access at every level, because each level prefetches ahead; and the operating system's page cache means "reading from disk" often isn't — a hot file lives in free RAM, which is why a database can look fast until its working set exceeds memory, and then fall off a cliff. When you hear "performance degraded gradually then collapsed", suspect a working set that outgrew RAM.

Concurrency control, in the order you'll need it

Race condition
Two threads read-modify-write the same value; one update is lost. counter += 1 is three operations, not one.
Mutex / lock
Only one thread in the critical section. Correct and slow; the cost is contention, where threads spend their time queueing rather than working.
Deadlock
A holds lock 1 and wants 2; B holds 2 and wants 1. Requires all four Coffman conditions; the practical fix is a global lock ordering — always acquire in the same order — plus timeouts.
Atomic operation
Compare-and-swap and friends: hardware-level, lock-free, the foundation of every concurrent data structure. INCR in Redis is this idea over the network.
Optimistic locking
Don't lock. Read a version number, and on write assert it hasn't changed (UPDATE … WHERE version = 7); retry if it has. Best when conflicts are rare — which is nearly always.
Pessimistic locking
SELECT … FOR UPDATE. Take the lock first. Correct under heavy contention, and a throughput ceiling — plus a deadlock risk you now own.
Immutability
The cheapest concurrency strategy: if nothing is mutated, nothing needs coordinating. This is why event logs, append-only stores, and copy-on-write structures are so common in distributed systems.

Section 02 · Foundations

Databases from scratch

More design rounds are lost on database questions than on any other topic, because "which database" is really four questions: what does an index cost, what does a transaction guarantee, what happens under concurrent writes, and what happens when one machine isn't enough. Answer those and the choice makes itself.

What an index actually is

A table without an index is an unordered pile of rows. Finding WHERE email = 'x' means reading every row — a sequential scan, O(n). An index is a separate, sorted structure — almost always a B+ tree — mapping column values to row locations.

A B+ tree stores keys in fixed-size pages (typically 8 KB) with a high branching factor: an internal page holds hundreds of keys, so a tree over a billion rows is only about four levels deep. That's four page reads to find any row instead of a billion. All actual values live in the leaf pages, which are linked together — which is why a B+ tree serves both point lookups and range scans efficiently.

The rules that follow from the structure

  • Indexes make writes slower. Every INSERT/UPDATE/DELETE must update every affected index. Five indexes means roughly six writes per write. "Add an index" is never free, and on a write-heavy table it can be the problem rather than the fix.
  • Composite indexes are left-prefix only. An index on (user_id, created_at) serves WHERE user_id = ? and WHERE user_id = ? AND created_at > ?, but not WHERE created_at > ? alone — the tree is sorted by user_id first. Column order is a design decision, and this is the single most common index mistake.
  • A covering index answers the query without touching the table. If the index contains every column the query needs, the database never follows the pointer to the row. Often a 10× win on read-heavy paths.
  • Low-cardinality columns barely help. An index on a boolean over 100M rows still points at 50M of them; the planner will correctly ignore it and scan.
  • A function on the column disables the index. WHERE LOWER(email) = 'x' can't use an index on email — you need an index on the expression itself.
  • Clustered vs secondary. In MySQL/InnoDB the table is the primary-key B-tree, so secondary indexes store the primary key and every secondary lookup costs a second descent. This is why a random UUID primary key hurts InnoDB — inserts land all over the tree instead of appending.

The N+1 problem is the application-level version of the same mistake: fetch 100 posts, then loop and fetch each author separately — 101 queries, each with a network round trip. Fix by joining, or by batching the second query with WHERE id IN (…). Mention it by name; it's the most common real-world database bug in web applications.

Transactions: what ACID actually promises

Atomicity
All of the statements in the transaction, or none. Implemented by a write-ahead log: changes are journaled before they're applied, so a crash mid-transaction can be rolled back on restart.
Consistency
The weakest and most misunderstood letter. It only means declared constraints (foreign keys, uniqueness, checks) hold before and after. It is not the "C" in CAP, which is a different property entirely.
Isolation
Concurrent transactions don't see each other's partial work — to the degree the isolation level promises. This is where the real complexity lives.
Durability
Once committed, it survives a crash. Which requires an fsync to actually reach the disk, and that's why commit latency has a floor — and why synchronous_commit = off makes a database dramatically faster and slightly untruthful.

In words: a dirty read sees uncommitted data. A non-repeatable read is reading the same row twice in one transaction and getting different values. A phantom is re-running the same WHERE and getting new rows. Write skew is the subtle one: two transactions each read a set, each check a constraint that currently holds, and each write — and the constraint is violated by the combination. The classic case is two doctors both cancelling their on-call shift because each sees the other still on call. Only serializable prevents it, and knowing that example is worth real credit.

MVCC is how modern databases give you this cheaply: instead of locking readers out, each transaction sees a consistent snapshot of the data as of its start, and writers create new row versions rather than overwriting. Readers never block writers and writers never block readers. The cost is version accumulation — Postgres needs VACUUM to reclaim dead tuples, and a long-running transaction holds back cleanup for the whole database. "Why did our disk fill up?" is very often this.

Transactions that span services

Once data lives in two systems, ACID stops applying and you have three options:

  • Two-phase commit. A coordinator asks everyone to prepare, then to commit. Correct, and it blocks: if the coordinator dies after prepare, every participant holds locks indefinitely. Rare in modern systems for exactly this reason.
  • Saga. A sequence of local transactions, each with a compensating action to undo it. Book the flight, book the hotel; if the hotel fails, cancel the flight. No isolation — an intermediate state is visible — so the business has to tolerate it, which usually it does.
  • Make it one transaction. Often the right answer is that the two things belonged in the same service and the same database, and the distribution was the mistake.

The answer that scores well

"Postgres, until a specific requirement forces something else." Then name the requirement that would force it: write throughput beyond a single primary, a document shape that changes per tenant, sub-millisecond reads, full-text relevance ranking. Interviewers are testing whether you reach for complexity by default — and a modern Postgres with JSONB, full-text search, and pgvector covers a startling amount of ground, which is itself a good thing to say.

Two operational details that show experience

Connection pooling. Every Postgres connection is a process using several megabytes; a few hundred is a lot. But 100 app servers × a 20-connection pool each is 2,000 connections, and the database falls over. The fix is an external pooler (PgBouncer) in transaction mode. Mentioning this unprompted signals you've run something.

Migrations without downtime. Adding a nullable column is instant; adding a NOT NULL column with a default rewrites the table and locks it. The safe pattern is expand then contract: add the new column, write to both, backfill in batches, switch reads, then drop the old one — four deploys instead of one, and no outage. This is a very common senior-level follow-up.

Complexity, properly

Big-O is not trivia. It is the language you use to justify a design choice in ten seconds, and it is scored in every coding round. The goal is to compute it correctly and quickly for code you just wrote — including the cases where the answer isn't obvious.

What the notation means

O(f(n)) is an upper bound on growth as n gets large. Constants and lower-order terms drop, because they stop mattering: 3n² + 500n + 90000 is O(n²), and for large enough n a 500× constant advantage loses to a single extra factor of n. Ω is a lower bound, Θ is both. Interviews say "O" and mean "tight bound"; nobody will correct you for saying O(n) instead of Θ(n).

What the constants do matter for: n is small (an O(n²) algorithm over 50 items is fine and simpler), or the constant is enormous (a "linear" algorithm doing a database round trip per element is not fast).

Recursion: draw the tree

The cost of a recursive function is (number of nodes in the call tree) × (work per node).

  • fib(n) naive: each call spawns two, depth n → about 2ⁿ nodes, O(1) each → O(2ⁿ).
  • Merge sort: each level splits in half (log n levels), each level does O(n) merging → O(n log n).
  • Binary search recursive: one branch survives per level → O(log n).
  • Permutations: n choices, then n−1, … → O(n!) nodes, O(n) to copy each → O(n · n!).

For divide-and-conquer, the master theorem in the only form you need: for T(n) = a·T(n/b) + O(n^d), compare d with log_b(a) — if d is larger the top level dominates (O(n^d)), if equal it's O(n^d log n), if smaller the leaves dominate (O(n^log_b a)). Merge sort is a=2, b=2, d=1 → equal → O(n log n).

Amortized: the dynamic array

Appending to a Python list is usually O(1), but occasionally the array is full and must be copied to a bigger one — O(n). Because the size doubles, that copy happens rarely enough that the average over any sequence of n appends is O(1). That is amortized O(1), and it is not the same as average-case: amortized is a worst-case guarantee over a sequence, not a probabilistic claim. Hash table insertion is the same story. Say "amortized" when it applies — it's a precision marker interviewers notice.

1 · sliding window — variable size, the shape that covers most of them
def longest_ok_window(s):
    """Longest substring satisfying a condition. The invariant: the window
    [left, right] is always valid at the bottom of the loop."""
    count = {}
    left = best = 0
    for right, ch in enumerate(s):
        count[ch] = count.get(ch, 0) + 1          # 1. grow right

        while len(count) > 2:                       # 2. shrink while INVALID
            count[s[left]] -= 1
            if count[s[left]] == 0:
                del count[s[left]]
            left += 1

        best = max(best, right - left + 1)         # 3. record
    return best

# Fixed-size variant: no while loop -- just evict s[right-k] once right >= k.
# Minimum-window variant: shrink while VALID, and record inside the while.

def lower_bound(a, target):
    lo, hi = 0, len(a)                # hi is exclusive
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < target: lo = mid + 1
        else:               hi = mid       # mid might be the answer -- keep it
    return lo                          # == len(a) if no element qualifies

# candidates never spot it. Trigger: "minimize the maximum X" or
# "maximum X such that it is still possible".
def ship_within_days(weights, days):
    def feasible(cap):                 # monotone: True stays True as cap grows
        used, load = 1, 0
        for w in weights:
            if load + w > cap:
                used, load = used + 1, 0
            load += w
        return used <= days

    lo, hi = max(weights), sum(weights)   # tightest and loosest possible answers
    while lo < hi:
        mid = (lo + hi) // 2
        if feasible(mid): hi = mid
        else:             lo = mid + 1
    return lo
3 · monotonic stack — next greater element
def next_greater(nums):
    """For each index, the next value to its right that is larger.
    Stack holds INDICES whose answers are still unknown, values decreasing."""
    res = [-1] * len(nums)
    stack = []
    for i, v in enumerate(nums):
        while stack and nums[stack[-1]] < v:   # v resolves everything smaller
            res[stack.pop()] = v
        stack.append(i)
    return res

# Each index is pushed once and popped once -> O(n) despite the nested loop.
# Say that out loud; interviewers check whether you know why it isn't O(n^2).
# Largest rectangle in a histogram is this template with the popped bar's
# width computed as (i - stack[-1] - 1).
4 · heap — top K, and why a MIN-heap finds the MAX elements
import heapq

def k_largest(nums, k):
    """Keep a min-heap of size k: its root is the smallest of the k best
    so far, so it is exactly the element to evict. O(n log k), O(k) space --
    beats sorting when k is small, and works on a stream that doesn't fit."""
    heap = []
    for v in nums:
        heapq.heappush(heap, v)
        if len(heap) > k:
            heapq.heappop(heap)        # drop the smallest
    return heap

def merge_k_sorted(lists):
    # Seed with the head of each list, then pull-and-replace. O(N log k).
    heap = [(lst[0], i, 0) for i, lst in enumerate(lists) if lst]
    heapq.heapify(heap)
    out = []
    while heap:
        val, li, idx = heapq.heappop(heap)
        out.append(val)
        if idx + 1 < len(lists[li]):
            heapq.heappush(heap, (lists[li][idx + 1], li, idx + 1))
    return out

def merge(intervals):
    intervals.sort(key=lambda x: x[0])          # sorting by START is the whole trick
    out = []
    for start, end in intervals:
        if out and start <= out[-1][1]:          # overlaps the last kept interval

        else:
            out.append([start, end])
    return out

def min_meeting_rooms(intervals):
    # The other interval shape: a difference array / sweep line.
    events = []

        events.append((s, 1))                  # a room is taken
        events.append((e, -1))                 # a room is freed
    events.sort()          # at equal times, -1 sorts first: a room frees before it fills
    cur = best = 0

from collections import deque

def shortest_path_grid(grid, start, goal):
    """BFS is the shortest path when every edge costs the same.
    The level-by-level inner loop is what lets you count distance."""
    rows, cols = len(grid), len(grid[0])
    q = deque([start])
    seen = {start}
    dist = 0
    while q:
        for _ in range(len(q)):              # drain exactly one level
            r, c = q.popleft()
            if (r, c) == goal:
                return dist
            for nr, nc in ((r+1,c), (r-1,c), (r,c+1), (r,c-1)):
                if (0 <= nr < rows and 0 <= nc < cols
                        and (nr, nc) not in seen and grid[nr][nc] != '#'):
                    seen.add((nr, nc))       # mark on PUSH, not on pop --
                    q.append((nr, nc))       # otherwise nodes enter the queue twice
        dist += 1
    return -1


def topo_order(n, edges):
    """edges are (u, v) meaning u must come before v.
    Returns [] if there is a cycle -- which is also the cycle detector."""
    adj = [[] for _ in range(n)]
    indeg = [0] * n
    for u, v in edges:
        adj[u].append(v)
        indeg[v] += 1

    q = deque(i for i in range(n) if indeg[i] == 0)
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    return order if len(order) == n else []
7 · union-find — with both optimizations, which is the whole point
class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n
        self.components = n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                     # already connected -> this edge is redundant
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra                    # attach smaller tree under larger
        self.parent[rb] = ra
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1
        self.components -= 1
        return True

# With both optimizations, amortized ~O(alpha(n)) -- effectively constant.
# Kruskal's MST is: sort edges by weight, union them, skip the False ones.
8 · backtracking — one shape, three problems (this is LC 40, Combination Sum II)
def combination_sum_ii(candidates, target):
    """choose -> recurse -> UNDO. The undo is what makes it backtracking."""
    candidates.sort()                    # enables both pruning and dedup
    res, path = [], []

    def backtrack(start, remaining):
        if remaining == 0:
            res.append(path[:])          # COPY -- path is mutated after this
            return
        for i in range(start, len(candidates)):
            if candidates[i] > remaining:
                break                    # sorted, so everything after is too big
            if i > start and candidates[i] == candidates[i-1]:
                continue                 # skip duplicates at the same depth
            path.append(candidates[i])
            backtrack(i + 1, remaining - candidates[i])
            path.pop()                   # undo

    backtrack(0, target)
    return res

# This exact code is LeetCode 40 (each candidate used ONCE, duplicates skipped).
# LeetCode 39, where a candidate may be REUSED, is one character different:
#     backtrack(i, remaining - candidates[i])     # i, not i+1
# and you drop the duplicate-skip line. Knowing which line encodes "reuse"
# and which encodes "no duplicates" is the whole family.
#
# Subsets: append path[:] at EVERY node instead of only at the base case.
# Permutations: iterate all indices with a `used` array instead of `start`.
9 · dynamic programming — 1-D and 2-D, with the questions that build them
# Build every DP by answering four questions OUT LOUD, in this order:
#   1. What is the STATE?        dp[i] = the best answer considering the first i items
#   2. What is the TRANSITION?   how does dp[i] follow from smaller states?
#   3. What is the BASE CASE?
#   4. What ORDER fills it?      every dependency must already be computed

def coin_change(coins, amount):
    # state: dp[a] = fewest coins summing to exactly a
    UNREACHABLE = amount + 1
    dp = [0] + [UNREACHABLE] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return -1 if dp[amount] == UNREACHABLE else dp[amount]


def longest_common_subsequence(a, b):
    # state: dp[i][j] = LCS of a[:i] and b[:j]. Two-string problems are
    # nearly always this grid -- edit distance is the same shape.
    m, n = len(a), len(b)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if a[i-1] == b[j-1]:
                dp[i][j] = dp[i-1][j-1] + 1       # match: consume both
            else:
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])  # drop one or the other
    return dp[m][n]

# Space optimization to mention (and only implement if asked): each row
# depends only on the previous row, so two rows suffice -> O(min(m,n)) space.

import heapq, math

def dijkstra(adj, src, n):
    """adj[u] = [(v, weight), ...]. Non-negative weights only --
    if there are negative edges the answer is Bellman-Ford, and saying
    that unprompted is worth more than the implementation."""
    dist = [math.inf] * n
    dist[src] = 0
    pq = [(0, src)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist[u]:
            continue                    # stale entry; we already did better
        for v, w in adj[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(pq, (dist[v], v))
    return dist

# A. Range SUM queries: O(n) build, O(1) per query.
def build_prefix(a):
    pre = [0] * (len(a) + 1)          # pre[i] = sum of a[0:i]
    for i, v in enumerate(a):
        pre[i + 1] = pre[i] + v
    return pre
# sum(a[l:r]) == pre[r] - pre[l]   <- the whole pattern, in one line


# B. Range UPDATES, one final read: the difference array (inverse trick).
def range_add(n, updates):
    diff = [0] * (n + 1)
    for l, r, val in updates:          # add val to a[l..r] inclusive
        diff[l] += val
        diff[r + 1] -= val               # cancel it just past the end
    out, run = [], 0
    for i in range(n):
        run += diff[i]
        out.append(run)
    return out
# m updates in O(m + n) instead of O(m * n). This is also the sweep-line
# used for "minimum meeting rooms" and for car-pooling problems.


# C. The high-value combination: prefix sum + hash map.
def subarrays_summing_to_k(nums, k):
    """Count subarrays with sum exactly k -- including negatives, so
    sliding window does NOT work here. This distinction gets tested."""
    seen = {0: 1}          # a prefix sum of 0 has occurred once (empty prefix)
    total = running = 0
    for v in nums:
        running += v
        total += seen.get(running - k, 0)   # how many earlier prefixes make this work
        seen[running] = seen.get(running, 0) + 1
    return total

Extensions worth naming: a 2-D prefix sum answers rectangle-sum queries with the inclusion–exclusion formula P[r2][c2] − P[r1][c2] − P[r2][c1] + P[r1][c1]; prefix XOR solves the same family of problems for XOR ranges; and if the array is mutable, prefix sums stop working and you need a Fenwick tree (below).

def single_number(nums):

def rotate_90_clockwise(m):
    """In place, O(1) extra space. The trick: transpose, then reverse rows.
    Deriving this on the spot is hard; recognizing it is easy."""
    n = len(m)
    for i in range(n):
        for j in range(i + 1, n):        # j starts at i+1 -- swapping twice undoes it
            m[i][j], m[j][i] = m[j][i], m[i][j]
    for row in m:
        row.reverse()
    # counter-clockwise = transpose, then reverse the COLUMN order (m.reverse())


def spiral(m):
    """Four moving boundaries. The two guards in the second half are the
    bug everyone hits on non-square matrices."""
    out = []
    top, bottom, left, right = 0, len(m) - 1, 0, len(m[0]) - 1
    while top <= bottom and left <= right:
        for c in range(left, right + 1): out.append(m[top][c])
        top += 1
        for r in range(top, bottom + 1): out.append(m[r][right])
        right -= 1
        if top <= bottom:                     # guard: the row may already be consumed
            for c in range(right, left - 1, -1): out.append(m[bottom][c])
            bottom -= 1
        if left <= right:                     # guard: same for the column
            for r in range(bottom, top - 1, -1): out.append(m[r][left])
            left += 1
    return out

18 · Greedy, and how to know it's safe

Greedy takes the locally best option and never reconsiders. It is O(n log n) and beautiful when it works, and quietly wrong when it doesn't — so the interview question is always why is greedy correct here?

The justification you should be able to give is the exchange argument: assume an optimal solution differs from the greedy one; show you can swap in the greedy choice without making it worse; conclude a greedy solution is also optimal. For interval scheduling — maximum number of non-overlapping meetings — sorting by earliest end time is optimal because taking the meeting that frees the room soonest never eliminates a possibility that another choice preserves. Sorting by start time or by duration is not optimal, and being able to say which sort key and why is the entire question.

Greedy vs DP, the decision rule

If a locally optimal choice provably can't hurt the global optimum, greedy works. If a choice's value depends on choices you'll make later, you need DP. Coin change is the canonical pair: with US denominations, always taking the largest coin is optimal; with coins {1, 3, 4} and a target of 6, greedy gives 4+1+1 = 3 coins and the optimum is 3+3 = 2. Have that counterexample ready — it's the fastest way to show you know why the distinction exists.

19 · Cyclic sort — the O(1)-space trick for values 1…n

Trigger: an array of n numbers containing values in the range 1 to n, and a question about a missing, duplicate, or first-positive number, usually with an O(1) space constraint. The insight: the array can be its own hash table, because value v belongs at index v−1.

cyclic.py
def cyclic_sort(nums):
    """Place every value v at index v-1. O(n): each swap puts one value
    permanently home, so there are at most n swaps despite the while."""
    i = 0
    while i < len(nums):
        target = nums[i] - 1
        if 0 <= target < len(nums) and nums[i] != nums[target]:
            nums[target], nums[i] = nums[i], nums[target]   # swap it home
        else:
            i += 1                                          # home already, or out of range
    return nums

# Then: the first index where nums[i] != i+1 is the missing/duplicate answer.
# Variant without sorting -- mark presence by NEGATING nums[abs(v)-1].
# Both are "use the array itself as storage", which is the pattern.

20 · Quickselect — top-K without the log

Trigger: the k-th largest/smallest element, when you want to beat the heap's O(n log k). Quickselect is O(n) average — it partitions like quicksort but recurses into only the side that can contain the answer.

quickselect.py
import random

def quickselect(a, k):
    """k-th SMALLEST, 0-indexed. Average O(n): n + n/2 + n/4 + ... = 2n.
    Worst case O(n^2) on adversarial input -- the random pivot is what
    makes that vanishingly unlikely, and saying so is the point."""
    lo, hi = 0, len(a) - 1
    while True:
        if lo == hi:
            return a[lo]
        p = random.randint(lo, hi)
        a[p], a[hi] = a[hi], a[p]              # move pivot out of the way
        pivot, store = a[hi], lo
        for i in range(lo, hi):               # Lomuto partition
            if a[i] < pivot:
                a[store], a[i] = a[i], a[store]
                store += 1
        a[hi], a[store] = a[store], a[hi]      # pivot lands at its final index

        if store == k:   return a[store]
        if store < k:    lo = store + 1
        else:            hi = store - 1

The comparison to state: heap is O(n log k) time, O(k) space, works on a stream, and preserves the input. Quickselect is O(n) average, O(1) space, needs the whole array in memory, and mutates it. For "top 10 of a billion streamed events" the heap is the only option; for "median of an array in memory" quickselect wins.

Two structures to recognize, not necessarily implement

If a problem needs range queries over data that changes, prefix sums are dead and you need one of these. Naming the right one and giving its complexity is usually enough; implementing a segment tree in 40 minutes is rarely the intent.

fenwick.py · a Fenwick / binary indexed tree is short enough to memorize
class BIT:
    """Prefix sums with point updates, both O(log n). The whole structure
    is the `i & -i` trick: jump by the lowest set bit."""
    def __init__(self, n):
        self.n = n
        self.tree = [0] * (n + 1)          # 1-indexed internally

    def add(self, i, delta):               # i is 0-indexed
        i += 1
        while i <= self.n:
            self.tree[i] += delta
            i += i & -i                    # move to the next range that covers i

    def prefix_sum(self, count):           # sum of the first `count` elements
        total, i = 0, count
        while i > 0:
            total += self.tree[i]
            i -= i & -i                    # strip the lowest set bit
        return total

    def range_sum(self, l, r):             # [l, r)
        return self.prefix_sum(r) - self.prefix_sum(l)

A segment tree is the more general version: O(log n) range query and update for any associative operation (sum, min, max, gcd), at ~4n space, and it supports lazy propagation for range updates. Use the sentence: "mutable range queries — Fenwick if it's prefix sums, segment tree if I need range min or range assignment."

def find_substring(text, pattern):
    n, m = len(text), len(pattern)
    if m > n: return -1
    BASE, MOD = 257, 10**9 + 7

    target = window = 0
    for i in range(m):
        target = (target * BASE + ord(pattern[i])) % MOD
        window = (window * BASE + ord(text[i]))    % MOD

    high = pow(BASE, m - 1, MOD)          # value of the leading character's place
    for i in range(n - m + 1):
        if window == target and text[i:i+m] == pattern:   # verify: hashes collide
            return i
        if i + m < n:
            window = ((window - ord(text[i]) * high) * BASE + ord(text[i+m])) % MOD
    return -1

Also know that KMP preprocesses the pattern into a failure table so the search never backtracks in the text, giving O(n+m) worst case with no hash collisions; and that tries (§04) beat both when you're matching many patterns at once.

The "implement it from memory" list

Five things that appear as whole interview questions, not as sub-steps. If you can write each in ten minutes without reference, you've covered a surprising amount of surface area:

  1. LRU cache — hash map plus a doubly linked list, O(1) get and put. (In Python you can say OrderedDict.move_to_end does this, then implement it manually anyway, because they want the linked list.)
  2. Min stack — a second stack holding the running minimum, so min() is O(1).
  3. Trie with wildcard search — the §04 trie plus a recursive branch on ..
  4. Iterator over a nested list — flatten lazily with an explicit stack, not eagerly.
  5. Rate limiter — the token bucket from §11, in-process rather than in Redis.

Section 07 · Algorithms

The review system

The difference between people who solve 300 problems and can't pass an interview and people who solve 120 and can is entirely here. Solving a problem once teaches you that problem. Solving it, forgetting it, and solving it again teaches you the pattern.

Why re-solving beats reading more

Recognition is not recall. Reading a solution produces a strong feeling of understanding that disappears within days, because you never practiced retrieving anything — you practiced following. The interview asks you to retrieve, from nothing, under observation. So the training has to be retrieval: blank page, timer, no reference.

The second reason is compression. The first time you solve "longest substring without repeating characters" you're solving a specific problem. The fourth time, across four different problems, you're recognizing sliding window with a validity condition — and that abstraction is what transfers to the problem you've never seen. You cannot form it from one exposure.

The three-pass method for every problem

  1. Pass 1 — attempt, hard-capped at 25 minutes

    Read the problem. Spend two minutes stating the pattern you think it is and why. Then solve it. Stop at 25 minutes whether or not you're done — going longer trains you to grind, and interviews don't reward grinding. Before you look anything up, write down the exact sentence describing where you're stuck.

  2. Pass 2 — study, not read

    Read the editorial or a strong solution until you can explain why it works, not just what it does. Then answer two questions in writing: what was the insight I missed? and what in the problem statement should have pointed me at it? The second question is the one that builds recognition speed. Close everything.

  3. Pass 3 — re-implement from blank, the next morning

    Not the same day — the next day, from an empty file, with no reference. If you can't, you didn't learn it; that's information, not failure. Re-read once and re-attempt the day after. A problem is not "done" until you've written it clean from nothing.

The spacing schedule

Every problem gets a rating when you finish, and the rating sets the next review date:

RatingMeaningNext reviewThen
4 — cleanSolved optimally inside the time cap, no hints, no bugs+21 daysRetire it if clean twice
3 — slowGot there, but over time or with a compile-fix loop+7 daysPromote to 4 if the next attempt is clean
2 — hintedNeeded a nudge, then finished it yourself+3 days—
1 — read itRead the solution, or couldn't finish+1 dayRe-implement from blank tomorrow, no exceptions

Any review that goes badly drops the rating back down and restarts the interval. In practice this means roughly 60% new problems and 40% reviews through weeks 1–2, inverting by week 4 — which is exactly what you want going into a loop.

Five ways people waste a month on this
  • Solving without a timer. Forty-five unhurried minutes on a medium teaches you nothing about performing in twenty-five observed ones.
  • Reading solutions instead of attempting. Feels efficient, builds recognition without recall, and collapses under interview conditions.
  • Chasing hards too early. The bulk of real interviews are mediums. Two clean mediums teach more than one heroic hard.
  • Never redoing anything. The most common failure. If your list only grows, you are collecting problems, not learning patterns.
  • Silent solving. You are training a skill you will perform out loud. Narrate every session, even alone, from day one — the first time you talk while coding should not be in an interview.

How many is enough

Roughly 120–150 problems solved to a rating of 4, spread across all twenty patterns, is a comfortable place to walk into a loop from. Two hundred shallow attempts is worse than a hundred deep ones. The honest test isn't a count at all: pick a random medium you've never seen, and see whether you can name the pattern within two minutes and produce a working solution within twenty-five. When that's reliably true, you're ready, whatever the number says.

Two candidates produce the same working function and get different scores. The difference is the twelve minutes before the first line of code and the four minutes after the last one.

The protocol

When you get stuck — a script, so you don't freeze
  1. Say that you're stuck, and where. "I have the recursion but I'm not seeing how to memoize the second parameter." Interviewers can only help a stated problem.
  2. Go back to the example. Do a bigger case by hand and watch what your hand does — that's usually the algorithm.
  3. Solve a simpler version. Drop a constraint: assume sorted, assume no duplicates, assume k=1. Then add it back.
  4. Say the brute force and start coding it. A working O(n²) beats a beautiful unwritten O(n). You can optimize with time left.
  5. Take the hint. If they say "what if you sorted it first", they are not making conversation.

The bugs that actually cost points

  • Off-by-one in binary search. Use the lo < hi form in §04 every time and stop reinventing it.
  • Mutating a list while iterating it. Iterate over a copy or build a new list.
  • Appending a reference instead of a copy in backtracking — res.append(path) instead of res.append(path[:]). Every result ends up identical and empty.
  • Marking visited on pop instead of on push in BFS — nodes enter the queue multiple times and the complexity quietly becomes exponential.
  • Integer division and negative numbers — Python's // floors toward negative infinity; most other languages truncate toward zero.
  • Default mutable arguments (def f(acc=[])) — shared across calls, and a classic.
  • Forgetting the empty input. Check it first, always, in the first line of the function.

Pick a language and stop thinking about it

Python unless you have a strong reason otherwise — the least syntax between your thinking and the whiteboard. Have these memorized so you never stall on mechanics: collections.defaultdict / Counter / deque, heapq.heappush/heappop/nlargest, bisect.bisect_left/insort, sorted(x, key=lambda v: (-v[1], v[0])), itertools.accumulate, and float('inf'). Know that list.pop(0) is O(n) and deque.popleft() is O(1) — that one difference has failed real candidates.

Step 1 in practice: the scoping questions that pay

Ask five, not fifteen. These five almost always change the design:

  1. Read or write heavy, and by what ratio? A 100:1 read ratio means caching and read replicas; 1:1 means the write path is the design.
  2. How stale can this be? Seconds of staleness unlocks async fan-out, denormalization, and caches. "Must be immediately consistent" removes all three.
  3. What is the latency target, at what percentile? p50 is a vanity number. Design against p99.
  4. How big is the largest entity, and the largest fan-out? The celebrity with 100M followers is the entire reason feed systems are interesting.
  5. Global or single region? Multi-region turns every consistency question into a hard one.
Phrasing that buys signal
  • "I'll assume X — tell me if that's wrong." Beats silence, and beats asking permission for every assumption.
  • "There are three ways to do this. I'll take B because of the write ratio; A wins if reads dominate." Naming the loser is the signal.
  • "That's a consistency question — let me finish the write path and come back to it in two minutes." Interviewers reward a driver.
  • "This is where I'd want a real number. If it's under 10k QPS, one Postgres box does it; over that, I shard."
Six ways candidates lose the round
  • Boxes with no arrows-with-nouns. Every arrow needs a protocol and a payload, or it's decoration.
  • Buzzword stacking. Naming Kafka, Redis, Cassandra and Spark in one breath without a reason each. Expect "why not just Postgres?" — and have the answer.
  • No numbers. Sharding without ever computing that the data doesn't fit on one machine.
  • Designing for 100× the stated scale. Over-engineering reads as poor judgment, not ambition.
  • Going silent while thinking. A few seconds is fine and normal. A long unexplained silence isn't — not because a stopwatch is running, but because the interviewer can't write down what they can't hear. "Let me think about the write path for a moment" costs nothing and buys all the silence you need.
  • Defending a choice past its evidence. When the interviewer pushes twice, they are usually handing you something. Take it.

Strategies, and when each is right

  • Cache-aside (lazy loading). App reads cache, misses, reads DB, writes cache. The default. Cost: every miss pays double latency, and the first request after a deploy is always a miss.
  • Write-through. Write DB and cache together. Cache is never stale; writes are slower and you cache things nobody reads.
  • Write-behind. Write cache, flush to DB asynchronously. Fast writes, and you lose data if the cache dies. Legitimate for counters and view stats, not for money.
  • Refresh-ahead. Proactively re-populate before TTL expiry for a known hot set. The fix for predictable, expensive keys.
Three cache failures worth naming out loud
  • Thundering herd / stampede — a hot key expires and 10,000 requests hit the DB at once. Fix: a per-key lock so one request refills (single-flight), or serve stale while one refreshes.
  • Cache penetration — repeated lookups for keys that don't exist bypass the cache entirely. Fix: cache the negative result with a short TTL, or a Bloom filter in front.
  • Cache avalanche — everything was populated at the same time, so everything expires at the same time. Fix: jitter the TTL (ttl = base + random(0, base/4)).

Sharding and consistent hashing

You shard when data or write throughput exceeds one machine — not before. The whole interview is in the choice of partition key:

  • Hash of entity id — even distribution, but range scans become scatter-gather across every shard.
  • Range (e.g. by time) — beautiful range scans, and the newest shard takes 100% of the writes. Classic hotspot.
  • Composite (tenant_id, timestamp) — usually the right answer for multi-tenant systems: locality within a tenant, spread across tenants.
  • Geography — locality and data residency, at the cost of cross-region joins.

Plain hash(key) % N remaps nearly every key when N changes. Consistent hashing places nodes and keys on a ring so adding a node only moves K/N keys; virtual nodes even out the distribution.

Know two neighbors of the idea, because "why a ring?" is a fair question. Rendezvous (highest-random-weight) hashing computes hash(key, node) for every node and takes the maximum — same K/N movement property, no ring and no virtual nodes to manage, at O(N) per lookup, which is fine for tens of nodes and not for thousands. Bounded-load consistent hashing adds a per-node capacity cap and spills past it, which is the answer when one key is genuinely hot and more vnodes won't help.

consistent_hash.py · the version you can write in an interview
import bisect, hashlib

class HashRing:
    def __init__(self, nodes=(), vnodes=150):
        self.vnodes = vnodes
        self.ring = {}          # hash -> node
        self.sorted_keys = []   # sorted hashes, for bisect
        for n in nodes:
            self.add(n)

    def _hash(self, key):
        # Full 128-bit digest, not a truncated prefix. With 100 nodes x 150 vnodes,
        # a 32-bit space collides often enough to corrupt the ring silently.
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add(self, node):
        for i in range(self.vnodes):        # virtual nodes smooth the distribution
            h = self._hash(f"{node}#{i}")
            self.ring[h] = node
            bisect.insort(self.sorted_keys, h)

    def remove(self, node):
        for i in range(self.vnodes):
            h = self._hash(f"{node}#{i}")
            del self.ring[h]
            del self.sorted_keys[bisect.bisect_left(self.sorted_keys, h)]   # O(log n), not a scan

    def get(self, key):
        if not self.ring: return None
        h = self._hash(key)
        # bisect_LEFT: we want the first node at or after h. bisect_right would
        # skip past a node whose hash equals the key's exactly.
        i = bisect.bisect_left(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[i]]

    def get_replicas(self, key, r=3):
        # The follow-up they always ask: a node dies -- where is the data?
        # Walk clockwise collecting R DISTINCT PHYSICAL nodes, skipping further
        # vnodes of a node already chosen. Forget that and all three "replicas"
        # can land on one machine, which is the classic implementation bug.
        if not self.ring: return []
        start, out = bisect.bisect_left(self.sorted_keys, self._hash(key)), []
        for step in range(len(self.sorted_keys)):
            node = self.ring[self.sorted_keys[(start + step) % len(self.sorted_keys)]]
            if node not in out:
                out.append(node)
                if len(out) == r: break
        return out

CAP, said correctly — and define the terms, because CAP uses them in a specific technical sense: consistency here means linearizability (every read sees the most recent completed write, as if there were one copy), not ACID's C; availability means every non-failing node returns a non-error response, which is a bar so high that almost no production system actually meets it. The consistency hierarchy is not a single line, and saying so correctly is a real signal. Eventual consistency is the floor. Above it sit the four session guarantees — read-your-writes, monotonic reads, monotonic writes, writes-follow-reads — which are mutually incomparable: none implies another, and you pick the ones your product needs. Above those: causal, then sequential, then linearizable. Multi-object transactions are a separate, orthogonal axis — read committed < snapshot isolation < serializable < strict serializability (see §02). Name the weakest guarantee that satisfies the product: "likes can be eventually consistent, but a user must read their own comment immediately, and the balance after a transfer needs serializable" is exactly the sentence they want.

Asynchrony: queues, logs, and the delivery question

A queue (SQS, RabbitMQ) distributes work; a message is consumed once and gone. A log (Kafka, Kinesis) is a replayable, partitioned, ordered sequence that many independent consumer groups read at their own offsets. Reach for a log when more than one system cares about the event, or when replay matters.

  • At-most-once: fire and forget. Losses allowed — metrics, maybe.
  • At-least-once: the real world. Retries cause duplicates, so consumers must be idempotent.
  • Exactly-once: does not exist over a network. What exists is at-least-once delivery plus idempotent processing, or a transactional log with offset commits inside the same transaction as the side effect.

Idempotency in practice: the client generates a key (Idempotency-Key: uuid), the server stores key → result before doing the work, and a repeat of the key returns the stored result instead of re-executing. Every payment API on earth works this way, and saying it earns real credit.

Ordering: Kafka guarantees order within a partition. If order matters per user, partition by user_id — and accept that one hot user is now one hot partition.

The outbox pattern solves the dual-write problem (write to DB and publish an event, atomically): write the event to an outbox table in the same transaction, and a change-data-capture reader tails the WAL and publishes it. Mention this when someone asks "what if the DB commit succeeds but Kafka is down?"

Bloom filters

A bit array plus k hash functions. Answers "definitely not present" or "maybe present" in O(k) with no false negatives. For n items and false-positive rate p: m = -n·ln(p) / (ln2)² bits and k = (m/n)·ln2. Practically: ~10 bits per element gives ~1% false positives — one billion keys in about 1.2 GB. Uses: skipping SSTable reads in an LSM tree, avoiding cache penetration, "have I seen this URL" in a crawler.

The follow-up is always deletion. You cannot remove an element from a standard Bloom filter — clearing its bits would break every other element that shares one. The three answers: a counting Bloom filter (4-bit counters instead of bits, 4× the space), a cuckoo filter (supports deletion, similar space, and gives you a lookup structure rather than just a membership bit), or rebuild and swap periodically, which is what most systems actually do. Also know that the false-positive rate degrades as you insert past the n you sized for — which is why RocksDB builds one filter per SSTable rather than one per database.

Proximity and geospatial indexing

Worth knowing cold — it turns up in ride-hailing, delivery, "nearby friends", and store locators.

  • Geohash — interleave latitude and longitude bits into a base-32 string. Cells are rectangles, not squares (precision 6 ≈ 1.2 km × 0.6 km at the equator) and they narrow toward the poles, so size precision off the shorter side. A shared prefix means spatial proximity, so a plain B-tree prefix scan becomes a proximity query and it works in any boring database. Weakness: cells near a boundary are far apart in string space, so query the cell and its eight neighbors.
  • Quadtree — recursively split a cell into four until it holds fewer than k points. Adapts to density, which geohash doesn't: Manhattan and the Pacific get very different tree depths. In-memory, needs rebuilding.
  • S2 / H3 — Google's and Uber's cell systems. H3's hexagons have uniform neighbor distance (every neighbour's centroid is equidistant, unlike a square grid's diagonals), which is why it wins for demand aggregation and surge pricing. Two caveats worth volunteering: cell areas still vary roughly 2× within a resolution, and the icosahedral projection forces exactly 12 pentagons per resolution.
  • The moving-object trick — don't index the drivers, index a grid and let drivers publish location every 3–5 s into a Redis GEOADD / hash keyed by cell. Reads are "give me cells within radius"; writes are cheap overwrites, and staleness of a few seconds is invisible to the user.

Keeping a system up

  • Timeouts on every network call. An unbounded call is a thread leak waiting for traffic.
  • Retries with exponential backoff and jitter. Backoff without jitter synchronizes your clients into a retry storm.
  • Circuit breakers — after n failures, stop calling for t seconds and fail fast. Prevents one slow dependency from consuming every thread you own.
  • Bulkheads — separate connection pools per dependency, so the failing one can't starve the healthy ones.
  • Graceful degradation — serve stale cache, drop personalization, return the non-ranked feed. Say what the degraded experience is; that's a product-minded answer.
  • Load shedding — reject early at the edge when saturated. A fast 503 is far better than a queue that times out after 30 s of held resources.
  • The golden signals — latency (p50/p95/p99), traffic, errors, saturation. Plus an SLO and an error budget: "99.9% of reads under 200 ms, measured at the edge" is what a real target sounds like.

Design 1 — URL shortener

The warm-up question. It looks trivial, which is exactly why the bar is "did you find the interesting part". The interesting part is ID generation and the read path, not the database.

Scope

In: create a short link (optional custom alias, optional TTL), redirect, click analytics. Out: user accounts, link editing, spam detection — mention that you're deferring them. Non-functional: redirect p99 under 50 ms measured at the edge — say the measurement point, because the document's own latency table puts a US cross-country round trip at 70 ms, so a 50 ms end-user p99 is physically impossible and stating one unqualified is a self-inflicted wound. Read-heavy, and the redirect path must survive the analytics pipeline being down.

Scale

100M new links/day → ~1,000 writes/s. Read:write of 100:1 → 100k reads/s average, 300k peak. Five years of links ≈ 180B rows × ~500 B = ~90 TB. So: sharded key-value store, aggressive caching, and the write path is trivially small.

The short code

Base62 (a–zA–Z0–9): 627 ≈ 3.5 trillion codes, so 7 characters is enough for a century. Three ways to make one:

If asked for globally-unique 64-bit ids without a central service, describe Snowflake: [1 unused sign bit | 41 bits ms-timestamp | 10 bits machine id | 12 bits sequence]. Deep dive: the redirect

The 301-vs-302 choice is the question, and the honest answer has three parts rather than one. A 301 is heuristically cached by browsers more or less indefinitely when you send no cache headers — so subsequent clicks never reach you at all: fastest possible redirect, zero click analytics after the first, and the link can never be retired. A 302 is not cacheable by default, so every click reaches you: full analytics, full load, and your CDN node caches nothing. The real answer is to pick your point on that line explicitly — "302 plus edge-side click aggregation if analytics fidelity is the product; 301 with an explicit short max-age if origin load is the constraint and sampled analytics are acceptable." Naming the header you'd set, and what your CDN does with it, is what separates this from a memorized line.

Whichever you choose, cache hit rate is high because link popularity is Zipfian — a Redis cache of the top few million codes serves most traffic and the KV store barely sees load.

Deep dive: the timeline representation

Each user's timeline is a time-ordered list of ~800 post ids. Truncate hard — nobody scrolls past a few hundred items, and unbounded lists are how you run out of memory at 3am. Only materialize timelines for active users (seen in the last 30 days); for everyone else, build on read and start pushing again once they return.

Now size it honestly, because this is where the naive number is wrong by an order of magnitude. 500M active users × 800 ids × 8 B of raw id is ~3 TB. But a Redis sorted set costs a skiplist node, a dict entry, and an sds string per member — realistically 60–100 B per entry, so the same timelines in sorted sets are 30–40 TB, which is a completely different purchasing decision. The fix is to stop using a sorted set: pack the ids into one fixed-width binary blob per user and pay the ~3 TB. Catching that gap between the data and its representation is a genuinely senior move.

One thing not to hand-wave: a precomputed timeline cannot be ordered by predicted engagement, because engagement predictions depend on request-time context — hour, device, session depth. The materialized list is a recency-ordered candidate set; ranking happens at read time (§15). Saying that explicitly avoids the most common hole in this design.

Pagination must be cursor-based (?after=<post_id>&limit=20), never offset-based: new posts arriving shift every offset and users see duplicates.

Deep dive: ordering and delivery

First, the storage arithmetic the design needs: 50B messages/day × ~200 B ≈ 10 TB/day, ~3.6 PB/year — so messages go to a horizontally partitioned wide-column store with age-based tiering, not to a relational primary.

Client timestamps are unusable — clocks lie and clients cheat. Assign a monotonic sequence number per conversation at the chat service, and let clients sort by it. Be ready for "how?", because that is a coordination question wearing a small hat: the practical answers are a single-writer partition owner per chat_id (route by hash, hold a lease — the same trick as Design 10), or an atomic INCR on a per-conversation counter, or a conditional write on (chat_id, seq) that retries on collision. Pick one and say what happens when the owner dies. Partition the message store by chat_id so a conversation's messages live together and a single-partition read serves the history; the primary key is (chat_id, seq), which makes "load 50 messages before X" one range scan.

Delivery is a three-state machine: sent (server has it), delivered (recipient's device acked), read (recipient opened it). Each is a separate small event flowing back on the same channel. For offline users, hold messages in a per-user inbox and drain it on reconnect — the client sends its last-known seq and the server replays forward.

Group chats flip the math: one message to a 500-person group is 500 deliveries. Keep groups bounded (that's why real products cap them), fan out through the same pub/sub, and for very large groups switch to a pull model — clients poll the conversation instead of receiving pushes.

Failure modes: a gateway node dying takes 50k connections with it (clients reconnect with backoff and jitter — without jitter you get a thundering herd against the registry) · duplicate sends on retry (client-generated message id, deduplicated server-side) · end-to-end encryption, if it comes up, means the server stores ciphertext and cannot do search, so search moves onto the device.

Design 4 — Nearby drivers (proximity service)

High-frequency writes against a spatial index — the opposite shape from the previous three, and a favorite because the naive answer (a SQL query with a bounding box) falls over immediately.

Scale

5M active drivers reporting every 4 s → 1.25M location writes/s. 1M rider searches/minute → ~17k reads/s. The write:read ratio is inverted from every other system here, and that is the whole design: writes must be O(1) with no index rebuild.

Why the obvious answer fails

SELECT * FROM drivers WHERE lat BETWEEN ? AND ? AND lng BETWEEN ? AND ? requires a two-dimensional index; a B-tree can only efficiently serve one of the two predicates, so the database scans a huge intermediate set. And 1.25M updates/s against an indexed table means constant index churn. You need a structure where a location update is a hash write.

The design: divide the world into cells (geohash precision 6 is ≈ 1.2 km × 0.6 km at the equator — it is not square, and it narrows with the cosine of latitude, so size your precision off the shorter dimension or your north–south coverage silently under-reads; or H3 resolution 8). Keep cell_id → {driver_id: (lat, lng, ts)} in Redis, sharded by cell. A location update is: compute the cell, and if it changed, remove from the old cell and add to the new one — two hash operations, no index. A search reads the rider's cell plus its neighbors, filters by true haversine distance, and returns the top K.

proximity.py · the read path, including the boundary bug everyone hits
def nearby(rider_lat, rider_lng, radius_km, k=10):
    # 1. Precision chosen so one cell is >= the search radius; otherwise
    #    "cell + 8 neighbors" is not enough coverage and you silently miss drivers.
    precision = precision_for(radius_km)
    cells = [geohash(rider_lat, rider_lng, precision)]
    cells += neighbors(cells[0])          # all 8 — a driver 50 m away can be in another cell

    # 2. One pipelined multi-get; 9 cells is a fixed, small cost.
    candidates = redis.pipeline_hgetall(cells)

    # 3. Exact filter. Cells are squares, the query is a circle.
    now = time.time()
    out = []
    for d in candidates:
        if now - d.ts > 30:            # stale: driver dropped off the network
            continue
        dist = haversine(rider_lat, rider_lng, d.lat, d.lng)
        if dist <= radius_km:
            out.append((dist, d))

    # 4. Top-K by heap, not a full sort -- see the top-K pattern in §04.
    #    NOTE the key=: on a distance tie Python would fall through to comparing
    #    the driver objects and raise TypeError. Classic heap-of-tuples bug.
    return heapq.nsmallest(k, out, key=lambda pair: pair[0])

Then divide, because the design depends on it. 1.25M location updates/s, at ~2 Redis operations each when a driver changes cell (remove from old, add to new), against ~100k ops/s per Redis node, is 25–40 nodes minimum before replication or headroom — and most updates don't change cell, so the realistic figure is nearer the low end. Sharding by cell id spreads that naturally. Doing this division out loud is the difference between proposing Redis and justifying it.

Density is the deep dive. A fixed grid puts 40,000 drivers in one Manhattan cell and zero in most ocean cells. Two answers: use a quadtree so cells split on density, or use multiple fixed precisions and pick the precision per query based on how dense the area is — the second is far easier to operate because it needs no rebuild. Say both, pick the second, and explain that operability is why.

Failure modes: a cell shard hot-spotting during an event (replicate hot cells read-only) · drivers oscillating across a cell boundary (hysteresis — only move cells after a real displacement) · Redis loss (the data is 4 seconds from being fully rebuilt by the drivers themselves, which makes durability a non-requirement — a genuinely nice thing to point out).

Section 13 · System design

Four harder designs

These four are chosen because each one forces a concept the first four don't: time-based work distribution, conflict resolution without a lock, extreme write compression, and correctness where being wrong costs money.

Design 9 — Distributed job scheduler

Prompt: schedule 100M jobs a day — one-off and recurring — with retries, at-least-once execution, and second-level precision. Deceptively hard, because the naive query is a landmine.

Scale

100M jobs/day → ~1,200/s average. But scheduled work is violently non-uniform: a huge fraction of cron entries fire at the top of the hour and at midnight, so peak is easily 50–100× average. Design for the spike, not the mean — that's the first thing to say.

Why the obvious query kills you

SELECT * FROM jobs WHERE next_run_at <= NOW() AND status = 'pending' LIMIT 100, polled every second by 50 scheduler nodes, means 50 queries per second all scanning the same index range and all fighting over the same rows. You get lock contention, duplicate pickup, and an index whose hot end every node hammers. The interview is about avoiding this.

The design: partition the time axis and the job space together. Jobs are hashed into N shards; each shard keeps its due jobs in a time-bucketed sorted set (Redis ZSET scored by next_run_at, or a table partitioned by minute). Each scheduler node holds a lease on a subset of shards from a consistent store, so exactly one node polls each shard — no contention, and rebalancing on node failure is a lease expiry rather than a coordination protocol.

Deep dive: the execution guarantee

You cannot have exactly-once. What you build is at-least-once with idempotent execution: the scheduler moves a job to in_flight with a lease deadline before enqueueing; the worker must finish and acknowledge before the lease expires or the job is redelivered. Every job carries an execution id, and the work it does must be safe to repeat under that id.

Retries use exponential backoff with full jitter — sleep = random(0, min(cap, base · 2^attempt)). Without jitter, a downstream outage produces synchronized retry waves that keep it down. After N attempts the job goes to a dead-letter queue with its failure history, because silently dropping work is worse than an alert.

The midnight thundering herd: if ten million cron jobs all specify 0 0 * * *, they all become due in the same second. Two mitigations, and you should offer both: deterministic jitter — spread each job by hash(job_id) % 60 seconds, which is stable across runs so it doesn't drift — and rate-limited dispatch per shard so the queue absorbs the spike rather than the workers.

Failure modes: clock skew between schedulers (use a single source for "now", or accept ±1 s and make it a documented guarantee) · a scheduler that pauses (GC, network) and resumes after its lease expired must not dispatch — check lease validity before every batch, a classic fencing-token problem · a job whose execution takes longer than its interval (either skip the overlap or queue it, but make it a per-job policy, and say which is the default).

Why a naive approach fails

Sending the whole document on every keystroke is correct and unusable. You need operations that can be transformed or merged to converge regardless of arrival order.

The architecture is a specialized LSM tree: agents push samples to an ingest tier, which appends to a write-ahead log and accumulates a head block in memory (the last couple of hours, uncompressed and queryable). Periodically the head block is compressed and written out as an immutable block to object storage, with its own index. Queries fan out across the blocks covering the time range, plus the head block, and merge. Old blocks are compacted and downsampled by a background job.

A series is identified by its label set — http_requests{service="api", region="us-east", status="500"} — and lookup is an inverted index: label pair → posting list of series ids, intersected across the query's matchers. This is literally the search-engine design from §15 applied to metrics, and pointing that out is a nice moment of synthesis.

Deep dive: cardinality is the thing that kills these systems

Every distinct combination of label values is a separate series with its own index entry and its own memory. Adding one label with a high-cardinality value — user_id, request_id, a raw URL with ids in it — multiplies your series count by millions and takes the cluster down. This is the number one production failure of every metrics system, and naming it unprompted is a strong signal. Defenses: enforce a per-metric series limit at ingest and reject beyond it, strip unbounded labels at the agent, expose cardinality as a first-class metric, and route genuinely high-cardinality data to a logging or tracing system instead — those are designed for it, and metrics are not.

Alerting runs the query set on a schedule (say every 15 s), which means the alert evaluator is your heaviest, most predictable query client — size for it explicitly. Add a for: 5m duration so a single bad scrape doesn't page anyone, deduplicate and group alerts before notifying, and support silences during deploys. And keep the alerting path independent of the long-term storage path, so you can still alert when the historical tier is down.

Design 12 — Payment processing

Prompt: charge a customer's card, and never double-charge, even when the network lies to you. The only design here where "eventually consistent" is not an acceptable answer, which makes it a favorite for testing rigor.

The two ideas that carry the whole design

1. A double-entry ledger. Don't store a balance you mutate. Store an append-only sequence of entries where every transaction has balanced debits and credits, and derive the balance by summing (with periodic materialized checkpoints so you're not summing ten years of history on every read). This gives you a complete audit trail, makes every state reachable from the log, and makes bugs detectable — if debits and credits don't sum to zero, something is wrong and you can prove it. Every real payment system works this way, and mutable-balance designs are how money quietly disappears.

2. An explicit state machine. created → authorized → captured → settled, with branches to failed, refunded, and the important one: unknown. Transitions are recorded as ledger entries. Nothing moves state except a valid transition, so an unexpected callback can't corrupt the record.

Deep dive: the timeout with an unknown outcome

This is the actual hard case, and the one that separates a good answer from a generic one. You call the payment processor and the connection times out. You do not know whether the charge happened. Retrying blindly may double-charge; giving up may take money without recording it.

The resolution has three parts: (a) pass your idempotency key to the processor so a retry with the same key is deduplicated on their side — every serious processor supports this; (b) before retrying, query the processor for the status of that key rather than re-issuing the charge; (c) if the status is still unknown, leave the payment in an explicit unknown state with a scheduled re-check, and never let it silently resolve to success or failure. Then the daily reconciliation job compares the processor's settlement file against your ledger line by line, and every mismatch is an alert that a human looks at. Reconciliation is not a nice-to-have here; it is the mechanism that makes the system trustworthy, and candidates who mention it unprompted stand out.

Consistency choice: this is the one system where you take strong consistency and pay for it. Ledger writes go through a single-leader relational database with serializable-or-close isolation; balance checks and debits happen in one transaction; cross-service flows use a saga with explicit compensation (refund) rather than two-phase commit, because holding locks across a third-party network call is untenable.

Failure modes worth naming: a duplicate webhook from the processor (dedupe on their event id, and treat webhooks as at-least-once) · out-of-order webhooks (the state machine rejects invalid transitions rather than trusting arrival order) · a partial refund arriving after a chargeback (model both as ledger entries, never as edits) · currency and rounding (integer minor units only — never floating point for money, and say this out loud, because it is a real disqualifier).

The four failures that separate levels

Training / serving skew

Features computed one way in a Spark job and another way in the serving path. The model sees a different world in production than in training, and the metric silently degrades. Fix: a feature store with one definition compiled to both paths, plus a continuous check comparing logged serving features against recomputed training features.

Label leakage

A feature that encodes the future — "number of items in cart at checkout" predicting purchase, or a feature aggregated over the whole dataset including post-event rows. Fix: point-in-time correct joins — every feature value is as of the prediction timestamp, never later. This is the single hardest thing about feature infrastructure.

Feedback loops

You only get labels for what you showed. The model recommends what it already believes, gets confirming clicks, and narrows forever. Fix: log the propensity of each impression, use inverse-propensity weighting, and reserve a small random-exposure slice as unbiased evaluation data.

Position & presentation bias

The top slot gets clicked because it is the top slot. Train naively on clicks and you learn "position 1 is good". Fix: include position as a feature during training and set it to a constant at inference, or model click = P(examined | position) × P(relevant).

Offline is a filter; online is the truth

Deployment is a staircase, and being able to name it is a strong shipping signal: offline eval on a held-out time-based split (never random — that leaks the future) → shadow mode, where the new model scores real traffic and its outputs are logged but not shown → interleaving for ranking, which needs a fraction of the traffic of an A/B test → canary at 1% → A/B test sized by a power calculation → ramp, with automatic rollback wired to the guardrail metrics.

The A/B numbers to have ready

Sample size per arm ≈ 16 σ² / Δ² for detecting an absolute lift Δ at 80% power and a 5% two-sided significance level. For a 2% baseline CTR and a 5% relative lift you need roughly a few hundred thousand users per arm — run it for at least one full week to absorb day-of-week effects. Randomize by user, not by request, or the same person sees both variants. Watch for network effects (social features spill between arms — switch to cluster randomization) and novelty effects (an early lift that decays by week two).

Three refinements that separate someone who has run experiments from someone who has read about them. Check SRM first — sample ratio mismatch, where a 50/50 split arrives as 50.4/49.6; it is the single most common reason a "significant" result is garbage, and it invalidates the test rather than adjusting it. Correct the variance for ratio metrics — CTR is measured per impression but randomized per user, so the naive binomial σ² understates the truth and real sample sizes land 2–5× above the textbook formula; use the delta method or cluster-robust standard errors. And use CUPED (variance reduction using pre-experiment data) to cut the required sample substantially for metrics with strong pre-period signal. Also: don't peek — repeatedly checking a running test inflates the false-positive rate unless you use a sequential test designed for it.

Indexing: chunking is the decision that matters most

  • Chunk on structure, not on character count. Split at headings and paragraphs, target ~500 tokens with ~15% overlap so a sentence spanning a boundary survives in one piece.
  • Keep the parent. Retrieve small chunks for precision, but pass the surrounding section to the model for context — "small-to-big" retrieval.
  • Prepend context to each chunk before embedding — document title, section path, and a one-line summary of what the parent document is about. A chunk reading "it increased 12% year over year" is unretrievable without it.
  • Store metadata for filtering — ACL groups, source, timestamp, language.   • Re-embed on model change. Changing the embedding model invalidates the entire index — 10M documents is a real re-indexing job, and planning for it (versioned indexes, dual-write, atomic swap) is a strong operational signal.
Size it, like any other index

10M documents × ~20 chunks each = 200M chunks. At 768 dims float32 that is ~614 GB of vectors plus the graph — comfortably a single beefy machine after int8 quantization, which is a genuinely useful thing to establish early, because it tells you this is not a distributed-systems problem and the effort belongs in retrieval quality instead. Per-query cost is (prompt tokens + output tokens) × price; with 8 chunks of 500 tokens you are paying for ~5k input tokens on every question, which is what makes prefix caching and small-model routing matter.

Grounding, and why "don't hallucinate" is a system property

You cannot prompt a model into being honest; you build a system where unsupported claims are detectable. Layer it:

  1. Require citations per claim — the prompt asks for spans tagged with chunk ids, and a post-processor verifies each cited id was actually retrieved. Hallucinated citations are trivially caught this way.
  2. Verify support — an entailment check (a small NLI model, or a second cheap LLM call) that asks "is this sentence supported by this chunk?" for the highest-stakes claims.
  3. Refuse deliberately — below a confidence threshold, answer "I don't have a document that covers this." But use a reranker score, not raw cosine similarity: embedding scores aren't comparable across queries (the distribution shifts with query length and specificity), so a fixed global cosine threshold over-refuses on some query shapes and under-refuses on others. A calibrated refusal rate is a shipped feature, not a failure.
  4. Show your work — render the source chunks alongside the answer so a human can check in two seconds.

Evaluation, which is where most candidates go vague

Split it in two, because the fixes are different. Retrieval: build a golden set of ~200 question→document pairs (labelled by hand, once, and worth the day it takes) and track recall@k and MRR. Generation: track faithfulness (fraction of claims supported by the retrieved context), answer relevance, and citation precision, scored by an LLM judge that you have calibrated against human labels on a sample. Then online: thumbs, follow-up-question rate, escalation-to-human rate, and time-to-answer. Say the failure taxonomy out loud — retrieval miss, retrieval hit but ignored, hallucinated detail, stale document, permission leak — because each one points to a different part of the pipeline.

Cost and latency: caching is the biggest lever, but be careful what you cache. A naive semantic cache — embed the query, return the cached answer above ~0.97 cosine — is a correctness bug in a system whose stated requirement is not making things up: "did revenue increase in Q3?" and "did revenue decrease in Q3?" sit far above 0.97 in any general embedding space and have opposite answers. Embeddings encode topic, not polarity. Cache the retrieval (safe — you re-generate against the same chunks), and gate any answer cache on a normalized exact-match or a cheap equivalence check. Prefix-caching the long system prompt is free money and has no such hazard. Stream tokens over SSE so time-to-first-token — the number users actually feel — stays under ~500 ms even when the full answer takes 5 s. Route by difficulty: a small model handles the easy majority, a large one handles the rest.

The four techniques to name

  • Continuous (in-flight) batching — the single biggest throughput win. Static batching waits for the slowest sequence in the batch to finish; continuous batching evicts finished sequences and admits new ones every step, typically a multiple-times improvement in real throughput.
  • Paged attention — allocate the KV cache in fixed-size blocks like OS virtual memory instead of one contiguous reservation per sequence. Kills the internal fragmentation caused by reserving for max context, and lets sequences with a shared prefix (a long system prompt) share physical blocks.
  • Chunked prefill — the simpler alternative to full disaggregation, and what most single-cluster deployments actually run. Split a long prefill into chunks and mix them into the same batch as in-flight decode tokens, so one long prompt can't stall every generating sequence. Chunk size trades time-to-first-token against inter-token latency, and it is the default in modern serving engines.
  • Prefill/decode disaggregation — prefill is compute-bound and parallel over the prompt; decode is memory-bound and sequential. They have opposite hardware profiles, so running them in one pool means one of them is always starving the other. Split the pools and you can size and autoscale each correctly.
  • Speculative decoding — a cheap drafter proposes several tokens, the large model verifies them all in one forward pass, and accepted tokens come nearly free. Two things to get right, because both are commonly overstated. First, rejection sampling preserves the target model's output distribution, not its exact output — token-identical only at temperature 0. Second, it is not safe to enable everywhere: it trades spare compute for latency, so at high batch sizes, where continuous batching has already saturated the GPU, verifying rejected drafts burns FLOPs for nothing and reduces aggregate throughput. Real stacks gate it on queue depth. Reported speedups fall from roughly 2× at batch 1 to about 1.2× at batch 128. Modern variants (EAGLE, Medusa, or plain n-gram / prompt-lookup drafting) are self-speculative and need no second model, which is why most teams use those rather than maintaining a separate draft model.

The platform around the model

Routing: classify difficulty and send most traffic to a small model, escalating only when needed. Multi-tenancy: per-team token quotas with a token-bucket limiter (§11) — GPU time is the scarce resource, so rate limit in tokens, not requests. Caching: prefix-cache long shared system prompts so prefill is not re-paid on every call. Autoscaling: scale on queue depth and time-to-first-token, not CPU; and cold-starting a GPU node means loading 35 GB of weights, so keep a warm pool — a 90-second scale-up is useless during a spike. Fallbacks: a queue with an admission deadline, then load-shed with a clear error, then a smaller model as the degraded tier.

Three more prompts, sketched

Ad click prediction

The twist: calibration, not ranking — the score is multiplied by a bid, so it must be a true probability. Use log loss; check a calibration plot; recalibrate with isotonic regression after any negative downsampling (and correct the intercept for the sampling rate). Latency budget is ~10 ms inside the auction. Features are enormously sparse and high-cardinality → hashing trick plus learned embeddings.

The twist: extreme imbalance (~0.1%), adversarial drift, and a 30-day label delay from chargebacks. Optimize PR-AUC. The twist: two thresholds, not one — auto-remove above the high one, auto-allow below the low one, and route the band between to human review. AI depth questions

These are the follow-ups that come after your diagram is on the board — the ones that decide whether the round reads as "designed a system" or "understands the system". Answer each in two or three sentences, then stop. Open one, answer it out loud before reading, then check.

Why is self-attention O(n²), and what do people do about it?

Every token attends to every other token, so the attention matrix is n×n — cost and memory both grow quadratically in sequence length. That's why context length is expensive, not just a config value.

Mitigations, roughly in order of how often they come up: FlashAttention (same math, tiled to keep the n×n matrix out of HBM — makes memory linear and is a pure win), sliding-window / local attention (each token sees a fixed neighborhood), sparse or strided patterns, and linear attention variants that approximate the softmax. Note that at inference with a KV cache, generating each new token is O(n) against the cache, not O(n²) — the quadratic term dominates prefill, and that asymmetry is exactly why prefill and decode get disaggregated.

What is the KV cache actually caching, and why does it dominate memory?

During generation, each new token attends to all previous tokens. Their key and value projections don't change, so you compute them once and keep them — turning per-token work from O(n²) into O(n). Without it, generating 1,000 tokens means re-running the prompt 1,000 times.

The cost is 2 × layers × kv_dim × bytes per token, per concurrent sequence — hundreds of KB per token at 70B scale, so a few thousand tokens is over a gigabyte per user in flight. It grows with concurrency and context, while weights are paid once. That's why the KV cache, not the model, sets your batch size. Grouped-query attention (many query heads sharing a few KV heads) is the standard fix and shrinks the cache several-fold at negligible quality cost; MQA is the extreme where all heads share one KV head. The third answer, now worth naming, is MLA (multi-head latent attention, used by the DeepSeek models): rather than reducing how many KV heads exist, it compresses what is stored — K and V are jointly projected into one shared low-rank latent plus a small decoupled RoPE key, and per-head K/V are reconstructed at inference. That cuts the cache by well over an order of magnitude versus same-shape MHA, at the cost of extra FLOPs and a much more awkward interaction with tensor parallelism, which is why GQA remains the industry default.

One derivation worth being able to do live: attention's arithmetic intensity during decode is n_query_heads / n_kv_heads — the GQA group size — independent of batch size and context length. So batching fixes the weight-matmul bottleneck but cannot fix the attention bottleneck, because every sequence has its own KV cache. That single fact is the structural argument for GQA, for MLA, for FP8 KV caches, and for prefix sharing.

RAG, fine-tuning, or a longer prompt — how do you choose?

They solve different problems, and saying so is the answer.

  • RAG for knowledge: facts that change, are too numerous to memorize, need citations, or need per-user access control. Updating means re-indexing a document, not retraining.
  • Fine-tuning (usually LoRA) for behavior: format, tone, a domain's vocabulary, following a rigid schema, or compressing a big model's capability into a small one for cost. It does not reliably install new facts, and it can't do per-user permissions.
  • Prompting / few-shot first, always — it costs an afternoon instead of a pipeline, and it establishes the baseline the other two must beat.

In practice mature systems use all three: a LoRA-tuned small model, RAG for facts, and a careful prompt. LoRA itself: freeze the base weights, train two low-rank matrices per layer so the update is W + BA with rank ~8–64 — under 1% of the parameters, one base model in memory serving many swappable adapters.

Your RAG system's answers are wrong. Walk me through debugging it.

Split at the retrieval boundary — the fixes are unrelated.

  1. Was the right chunk retrieved at all? Check recall@k against your golden set. If no → chunking strategy, embedding model, missing hybrid lexical path, or a metadata filter that emptied the results.
  2. Retrieved but not used? Check position in the context (models attend less to the middle of long contexts — put the best chunks at the edges), context crowding (8 good chunks beat 50 mediocre ones), and whether the prompt actually instructs grounding.
  3. Used but wrong? The source document is stale or contradicts another one. That's a data problem: add recency to ranking, and detect contradictions at index time.
  4. Nothing wrong retrieved, answer invented anyway? Missing refusal threshold and missing citation verification.

The meta-point: you need per-stage metrics, or every failure looks identical from the outside.

How do you detect that a deployed model has degraded, before the business metric does?

Labels arrive late, so watch the things that don't need labels:

  • Feature drift — population stability index or a KS test per feature against the training distribution. PSI over ~0.2 is the usual "look at this" line.
  • Prediction drift — the distribution of your model's own scores shifting is the earliest cheap signal.
  • Data quality — null rates, cardinality explosions, a schema change upstream. Most "model degradation" is actually an upstream pipeline that changed a unit or started sending nulls.
  • Delayed-label metrics — recompute AUC on a rolling window as labels land, and alert on the trend.

Distinguish data drift (inputs moved, P(X) changed) from concept drift (the relationship moved, P(y|X) changed). Data drift may be harmless; concept drift usually requires retraining — though not if it is confined to a region of the input space that carries no traffic, which is worth saying rather than claiming "always". And keep a holdout of un-personalized traffic so you have an unbiased baseline to compare against.

A feature is missing at serving time. What does your system do?

Never crash, and never silently send a zero — a zero is a real value to the model and it will confidently produce nonsense. Decide the policy per feature at training time: impute with the training median, use a dedicated "missing" indicator column, or (with tree models) let the model learn the missing branch natively.

Critically, train with missingness: randomly drop features during training at roughly the rate the serving path actually fails, so the model is robust to it. And have a tiered fallback for the whole service — full model → model without real-time features → simple heuristic → a static default ranking. Being able to name that ladder is what makes this a systems answer instead of a modeling one.

Why gradient-boosted trees instead of a neural network?

On tabular data with a few hundred features and modest volume, GBDTs (XGBoost, LightGBM) usually win outright: they handle mixed types and missing values natively, need almost no feature scaling, train in minutes on a CPU, and give you feature importances that let you debug. Neural networks start to pull ahead when you have very high-cardinality categorical features that benefit from learned embeddings, multi-task heads sharing a trunk, unstructured inputs (text, image, audio) in the mix, or enough data that end-to-end representation learning pays for itself.

Most large-scale ranking systems end up with both — trees in the cheap early stage, a deep multi-task model in the expensive final stage. Starting with the tree baseline and showing the network beat it is the answer that reads as experience.

Your offline metric improved but the A/B test was flat or negative. Why?

A genuinely common situation, and the diagnosis list is the answer:

  • The offline metric is computed on logs generated by the current model — it rewards agreement with the incumbent, not quality. Correct with propensity weighting or evaluate on a random-exposure slice.
  • Training/serving skew — the model you tested offline is not the model that ran.
  • The offline metric doesn't proxy the online one. AUC up, watch time flat, because AUC weights all pairs equally and users only see the top 5.
  • System effects the offline eval can't see — the better model is slower, and the added latency costs more engagement than the ranking gained. Latency is a ranking feature.
  • Underpowered test, or novelty effects that mask a real long-term gain.
How do you evaluate an LLM feature that has no single right answer?

Build a layered harness rather than looking for one number. Deterministic checks first — schema validity, does it compile, did it cite a real id, regex constraints. These catch most regressions and cost nothing. Then a golden set of a few hundred inputs with human-written references, scored by an LLM judge with a rubric — and calibrate that judge against human labels on a sample, reporting agreement, because an uncalibrated judge is just a vibe. Then pairwise comparison of the new version against the current one, which is far more reliable than absolute scoring. Then online: thumbs, retry rate, conversation abandonment, escalation to a human.

Two things to say that signal experience: pin the temperature for eval runs so you're measuring the change and not sampling noise — while noting that temperature 0 is not true determinism on a GPU (batching and kernel nondeterminism still move outputs), and that if you serve at temperature above 0 then a temperature-0 eval measures a model you don't ship, so run several seeds and report variance; and keep a regression suite of every past failure — production incidents become test cases, exactly as in normal software.

What is prompt injection, and how do you actually defend against it?

Any untrusted text that reaches the model — a retrieved document, a web page, a user's file — can carry instructions, and the model has no reliable way to distinguish data from instruction. In a RAG system the injected text is inside the retrieved context by design, which is what makes it structural rather than incidental.

There is no prompt that fixes it, so defend at the system level: least privilege (the model's tools have exactly the permissions of the current user, and read-only wherever possible), human confirmation for consequential actions (sending, deleting, paying), output filtering (never render model-produced links or markup unescaped; strip exfiltration vectors), separation (untrusted content clearly delimited and marked as data), and monitoring for anomalous tool-call patterns. The honest framing — "I treat model output as untrusted input to the rest of the system" — is the answer they're looking for.

Quantization: what breaks, and when do you accept it?

Weights are stored in fewer bits — fp16 → int8 → int4 — cutting memory and, because decoding is bandwidth-bound, increasing throughput roughly proportionally. Post-training quantization (GPTQ, AWQ) needs only a small calibration set and takes minutes; quantization-aware training costs a training run and recovers more quality.

What degrades first: outlier activations (which is why int8 schemes keep a few channels in higher precision), long-context coherence, and rare-token or non-English performance — averages on a benchmark can look fine while a specific slice falls apart. So the rule is: quantize, then evaluate on your own task, not on a public leaderboard. int8 is usually free; int4 is a real tradeoff you should measure. And a quantized larger model generally beats a full-precision smaller one at the same memory budget — a useful, concrete thing to assert.

How do you serve embeddings for 100M items that change constantly?

Separate the two rates of change. The model changes rarely — but when it does, every vector is invalid, so you version the index, backfill into a new one, and swap atomically. Items change constantly — so run a streaming path: on item update, re-embed and upsert into the index.

Real ANN indexes vary in how well they take incremental writes (HNSW handles inserts but degrades with heavy deletion churn), so the standard pattern is a large immutable base index rebuilt nightly plus a small in-memory delta index for recent changes, querying both and merging — the same read-optimized/write-optimized split as an LSM tree. Deletions go into a tombstone set applied as a post-filter until the next rebuild.

How do you handle 0.1% positive class?

In order of what actually helps: pick the right metric (PR-AUC, precision at a fixed recall — not accuracy, not ROC-AUC), set the threshold from the cost matrix rather than at 0.5, downsample negatives for training speed (then correct the predicted probabilities for the sampling rate, or your calibration is wrong by a large factor), and use class weights or focal loss. Synthetic oversampling like SMOTE is worth mentioning and usually worth skipping — it rarely helps on high-dimensional real data and it can leak across a validation split if applied before the split.

The framing that lands: the imbalance isn't the problem — the asymmetric cost is. Design around the cost, and the metric and threshold follow.

What's in a feature store, and why not just a database?

It solves three specific problems a plain database doesn't. One definition, two paths: the same feature logic compiled into a batch job for training and a low-latency lookup for serving, which is the structural fix for training/serving skew. Point-in-time correctness: joining features to labels as of each event's timestamp, so no future information leaks into training — doing this correctly by hand in SQL is where leakage bugs live. Reuse and discovery: features are shared across teams and models instead of re-derived slightly differently in five pipelines.

Architecturally it's an offline store (columnar, for training) plus an online store (key-value, for serving), fed by batch and streaming pipelines, with a registry of definitions and freshness SLAs. If the interviewer pushes on cost, the honest answer is that it's overhead for one model and essential at ten.

Model too big or too slow for the latency budget. Options?

Ordered by how much you give up: quantize (usually free at int8) · distill into a smaller student trained on the teacher's soft outputs, which typically keeps most of the quality at a fraction of the size · cache the predictions that repeat, and precompute anything that doesn't depend on the request · make it multi-stage so the expensive model only sees a few hundred candidates · batch on the server with a few milliseconds of queueing delay to raise GPU utilization dramatically · prune or use a smaller architecture · and finally relax the budget — sometimes the right answer is to render a fast approximate result immediately and refine it asynchronously.

Explain a mixture-of-experts model in the way an interviewer wants to hear it.

Replace the dense feed-forward block with many expert blocks plus a router that sends each token to the top-k experts. (Say "top-k", not "k=2" — that was the Mixtral generation; current fine-grained MoE designs route to 6–8 of many smaller experts plus one or two always-on shared experts.) Total parameters grow enormously while active parameters per token stay small — so you get the quality of a much larger model at roughly the compute of a small one.

The systems cost is the part worth naming: all experts must be resident in memory even though most are idle, so MoE trades memory for compute, which is the opposite of what most serving setups are optimized for. Add load balancing to stop the router collapsing onto a few experts — an auxiliary loss classically, or the newer loss-free bias-adjustment schemes — and expect expert-parallel all-to-all communication across GPUs. It is a throughput-and-quality win, not a memory win.

The serving gotcha, which is the part that shows systems thinking: at small batch sizes MoE has worse arithmetic intensity than a dense model with the same active parameter count, because you read many experts' weights to serve very few tokens. MoE needs large batches to pay off. So "should we serve an MoE model?" is really "will our traffic keep the batches full?"

How do you decide between batch and real-time inference?

Ask what the input depends on. If a prediction depends only on things known in advance (user history, item catalog) and the set of inputs is enumerable, precompute in batch and serve it as a lookup — orders of magnitude cheaper, trivially cacheable, and it can't time out. If the prediction depends on the request itself (the query, the current session, the candidate set), it has to be real-time.

Most large systems are hybrid, and describing the split is the good answer: user and item embeddings computed nightly in batch, the interaction scored in real time. There's also near-real-time — a streaming job maintaining counters and short-window aggregates — which covers most "but it needs fresh data" objections at a fraction of the cost of per-request computation.
