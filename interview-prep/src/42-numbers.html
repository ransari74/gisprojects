Section 02

Numbers & capacity math

You need maybe twenty numbers memorized and one arithmetic habit. The habit: round everything to one significant figure and use powers of ten. Nobody has ever failed a loop for saying 100k QPS when the true answer was 116,530.

Latency, to the nearest order of magnitude

OperationTimeWhat it implies
L1 / L2 cache reference~1 ns / ~4 nsFree. Never a design consideration.
Main memory reference~100 ns~10M random reads/sec/core. In-memory beats disk by ~1000×.
Read 1 MB sequentially from memory~10 µsMemory bandwidth ≈ 100 GB/s on modern hardware.
SSD random read (4 KB)~100 µs~10k–100k IOPS per device. This is why LSM trees batch writes.
Read 1 MB sequentially from SSD~200 µs~1–5 GB/s. Sequential beats random by ~100×. Design for sequential.
Round trip within a datacenter~0.5 msYour service-to-service tax. Ten hops = 5 ms floor.
Disk seek (spinning)~10 msArchival only. If someone says HDD, they mean cold storage.
Cross-country round trip (US)~70 msThe reason CDNs and regional replicas exist. Physics, not engineering.
Round trip across the world~150–250 msAny synchronous cross-continent call is a design smell.

The worked example: do this out loud, in 90 seconds

Prompt: design a photo-sharing service with 500M daily active users. Here is the entire estimation, at the level of detail you should actually speak.

Back-of-envelope · say the units every time
# 1. Traffic
DAU                = 500M
posts/user/day     = 0.2          # 1 post every 5 days — state the assumption
writes/day         = 100M
write QPS (avg)    = 100M / 100k s   = 1,000/s
write QPS (peak)   = 3x               = 3,000/s

reads/user/day     = 50           # opens the feed a few times, ~15 photos each
reads/day          = 25B
read QPS (avg)     = 25B / 100k s    = 250,000/s
read QPS (peak)    = 750,000/s          # read:write = 250:1 -> CDN + cache is the design

# 2. Storage
photo (orig+derivs)= 2 MB
storage/day        = 100M x 2 MB     = 200 TB/day
storage/year       = 200 TB x 365    ≈ 70 PB/year   # -> object store + lifecycle tiering, not a DB

metadata/photo     = 500 B            # ids, caption, geo, timestamps, counters
metadata/year      = 100M x 365 x 500 B ≈ 18 TB/year  # -> fits sharded Postgres/Cassandra fine

# 3. Bandwidth
egress (peak)      = 750k reads/s x 200 KB (served size) ≈ 150 GB/s
                     # no origin serves that -> CDN offload at 95%+, origin sees ~7 GB/s

# 4. Cache sizing (the 80/20 read)
hot set            = 20% of a day's reads over distinct photos
                   ≈ 5B reads -> ~50M distinct hot photos x 200 KB = 10 TB
                     # -> too big for RAM; cache metadata in Redis (50M x 500 B = 25 GB, easy),
                     #    cache bytes at the CDN edge.
What the estimate bought you

Four design decisions fell out of arithmetic, and you can now defend each one: object storage plus CDN (70 PB/year, 150 GB/s egress), metadata in a sharded relational store (18 TB/year is small), a Redis metadata cache but not a byte cache (25 GB fits, 10 TB doesn't), and an asynchronous write path for derivative generation (write QPS is trivial, but 2 MB × transcodes is not). That is the whole reason step 2 exists.
