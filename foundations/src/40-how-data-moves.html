How data moves.

Book three covered data sitting still. This one covers it in flight — between a browser and a server, between two services, and through a queue that decouples them. Roughly half of it will be familiar in substance and unfamiliar in vocabulary, because a Kafka consumer group and an HTTP retry are solving the same problem at different scales. The other half — the network itself — is genuinely new, and it is short.

Chapter one

One request, end to end

"You type a URL and press enter — what happens?" has been an interview question for twenty years because a full answer touches everything. Here it is as a spine you can hang the rest of the book on.

  1. The URL is parsed

    https://api.example.com:443/v1/users?id=42#top splits into scheme (which sets the default port and demands encryption), host, port, path, query, and fragment. The fragment after # is never sent to the server — browser-only. That detail alone decides analytics questions.

  2. DNS turns the hostname into an IP address

    Browser cache, then OS cache, then a recursive resolver which — if it has nothing cached — walks the hierarchy: root, then the .com servers, then the authoritative server for example.com. Each answer carries a TTL governing how long it may be cached.

    Why it matters in design: DNS is the first place you can do load balancing and failover, by returning different addresses to different regions. And the TTL is why DNS failover is never instant — clients keep the old address until it expires. Modern services prefer anycast: one address announced from many locations, with the network routing to the nearest.

  3. TCP connects — the three-way handshake

    SYN, SYN-ACK, ACK: one full round trip before any data moves. One millisecond inside a datacenter, seventy across a continent. This is why connection reuse and pooling matter so much, and why a service that opens a fresh connection per request is slow for reasons unrelated to its code.

    TCP gives ordered, reliable, congestion-controlled delivery. It costs you head-of-line blocking — one lost packet stalls everything behind it. UDP gives none of the guarantees and none of the cost, which is why video calls and DNS use it and handle loss themselves.

  4. TLS negotiates encryption

    The client offers cipher suites, the server presents a certificate chain, the client validates it, both derive a shared key. TLS 1.3 does this in one round trip. In practice this happens at the CDN or load balancer close to the user, so the expensive handshake crosses a short distance.

  5. The request reaches a load balancer, not a server

    Chapter three. The address you resolved almost certainly belongs to a load balancer.

  6. A server handles it

    The kernel accepts the connection, the app reads it off a socket, routes it to a handler — and the handler mostly calls other things. As Book 2 established, nearly all of the wall-clock time is spent waiting on those calls.

  7. Caching decides whether any of this happens again

    Cache-Control: max-age=3600 lets any cache reuse the response for an hour. ETag plus If-None-Match lets a client ask "has it changed?" and get a tiny 304 Not Modified instead of the body. Getting these headers right removes more load than most code optimizations.

Chapter two

How services talk to each other

HTTP methods, and the property that matters

MethodIdempotent?Means

DELETEyesRemove. The second call returns 404, but the state is the same — that is what idempotent means.

Idempotency is the load-bearing concept in this entire book, and you already own it: an Airflow task that can be re-run without duplicating rows is idempotent, which is what makes retries safe. Same property, same reason, different scale.

Status codes worth knowing precisely, because the distinctions get asked: 401 means not authenticated, 403 means authenticated but not allowed. 502 means a bad response from upstream, 503 means unavailable — try later, 504 means upstream timed out. Those two triples separate people who have debugged production from people who have not.

Three ways to shape an API

REST
Resources as URLs, verbs as HTTP methods, JSON bodies. Universal, cacheable by every proxy in existence, debuggable with curl. Costs: over-fetching, under-fetching, and the N+1 pattern where a list view triggers one request per item.
gRPC
Binary protobuf over HTTP/2 with a strict schema and generated clients. Much smaller payloads, faster serialization, native bidirectional streaming. The default for internal service-to-service traffic. Costs: not human-readable, needs a proxy for browsers, and schema evolution takes discipline — the same discipline you apply to an Avro schema registry.
GraphQL
The client asks for exactly the fields it needs in one round trip. Excellent for mobile and for many-shaped frontends. Costs: caching is hard (everything is a POST to one endpoint) and an unbounded query is an accidental denial of service, so you need depth limits and query cost analysis.

Pagination deserves its own mention because designs get it wrong constantly. Offset pagination (LIMIT 20 OFFSET 4000) is easy and wrong at scale: the database still scans the skipped rows, and any insert shifts every offset so users see duplicates. Use cursor pagination — pass the last seen sorted key and ask for what comes after it. It is O(1) regardless of depth and stable under concurrent writes.

Chapter three

Load balancing

A load balancer is a scheduler for requests. You already understand the job — it is what YARN or Kubernetes does for your executors, one abstraction layer up.

Algorithms: round-robin (simple, ignores that requests differ in cost), least-connections (usually the best default), consistent hashing on a key (when you want cache affinity — the same user hitting the same node), and power of two random choices — pick two backends at random and send to the less loaded one, which gets most of the benefit of least-connections without maintaining global state. That last one is a genuinely elegant result and worth knowing by name.

Health checks, and the trap in them

A shallow check asks "does the port accept a connection?" — which will happily route traffic to a process whose database pool is exhausted and which fails every request. So you make the check deep, verifying dependencies. Now one slow database marks your entire fleet unhealthy simultaneously, and the load balancer has nowhere to send anything. Both failure modes are real and they are opposites.

The resolution: a shallow check for routing decisions, and a separate deep check for alerting. Take a node out of rotation only for problems specific to that node. This is a small design detail that reliably distinguishes people who have operated a service.

Chapter four

Synchronous, asynchronous, and the queue

The most consequential structural decision in most designs is which work happens while the user waits and which happens after. Get it wrong in one direction and the product feels broken; wrong in the other and it feels slow.

Do it synchronously when the caller needs the result to continue, when it is fast and reliable, or when failure must be reported immediately. Do it asynchronously when the work is slow, when it can fail and be retried, when several systems care about the event, or when you want to absorb a spike rather than pass it downstream.

The classic example: a user uploads a photo. Synchronously, you store the bytes and return — a few hundred milliseconds. Asynchronously, you generate thumbnails, run moderation, extract metadata, and update feeds. If you did all of that synchronously, the upload would take thirty seconds and fail whenever the moderation service hiccupped.

The heuristic: if more than one system cares about the event, or if you might ever want to reprocess it, use a log. Which is most of the time in data-heavy architectures, and is why Kafka became infrastructure rather than a component.

Ordering, and the price of it

Kafka guarantees order within a partition, not across a topic. So if order matters per user, you partition by user_id — and you accept that one very active user is now one hot partition. That is the skew trade again, and it is unavoidable: ordering and parallelism are in direct tension, and you buy one with the other.

Chapter five

Delivery semantics, and the myth of exactly-once

Three levels, and only one of them is real in the general case.

  • At-most-once. Send and forget. Losses are acceptable — maybe for some metrics.
  • At-least-once. Retry until acknowledged. This is the real world, and it produces duplicates, because the acknowledgement can be lost after the work was done.
  • Exactly-once. Does not exist over a network, as a delivery guarantee. What exists is at-least-once delivery plus idempotent processing.
Why it cannot exist, in one paragraph

You send a message and get no reply. Two things are indistinguishable from where you stand: the message never arrived, or it arrived, was processed, and the acknowledgement was lost. If you retry, you may duplicate. If you do not, you may lose. No protocol resolves that ambiguity — the information simply is not available to you. So you choose which failure to accept, and the universal choice is: retry (accepting duplicates) and make the processing idempotent (so duplicates do not matter).

Idempotency in practice

The standard mechanism: the client generates a unique key, sends it with the request (Idempotency-Key: 7f3e…), and the server stores key → result before doing the work. A repeat of the same key returns the stored result rather than re-executing. Every payment API on earth works this way.

The variants, in the order you should consider them: make the operation naturally idempotent (set a value rather than increment it — the best answer where possible); deduplicate on a natural key (a unique constraint on the event id, letting the database reject the duplicate); or store processed ids explicitly. All three are things you have done in a pipeline to make it re-runnable.

What Kafka's "exactly-once" actually covers

Kafka does offer exactly-once processing semantics, and it is worth knowing precisely what that means because it is frequently overstated. It is built from two things: an idempotent producer (each producer has an id and per-partition sequence numbers, so the broker discards duplicates from retries) and transactions that atomically commit the output records and the consumer offsets together, with downstream readers set to read only committed data.

So a read-process-write pipeline that stays inside Kafka gets real exactly-once. The moment your side effect leaves that boundary — an email, a payment, a row in someone else's database — you are back to at-least-once plus an idempotency key. Saying that sentence answers the follow-up before it is asked.

The dual-write problem, and the outbox

Here is a bug that appears in almost every first design: you write a row to your database and publish an event about it. Two systems, two writes, no transaction across them. If the database commit succeeds and the publish fails, the event is lost forever and the two systems disagree permanently.

The fix is the outbox pattern: write the event into an outbox table in the same transaction as the data change. A separate process then reads the outbox — often by tailing the write-ahead log — and publishes. Atomicity comes free because both writes are in one local transaction.

Which is change data capture, which is the next chapter, and which you already run.

Chapter six

Streaming, stated precisely

This chapter is mostly review for you. Its value is that it gives your existing knowledge the exact words a design interview expects, so read it for vocabulary rather than for concepts.

Event time vs processing time
An event happened at 10:00 and arrived at 10:07 because a phone was in a tunnel. Windowing on processing time is easy and gives wrong answers; windowing on event time is correct and forces you to decide how long to wait.
Watermark
The formal answer to "how long do I wait": an assertion that no more events older than time T are expected, so windows up to T can be closed. It is a heuristic — aggressive means dropped data, conservative means stale results.
Allowed lateness
A grace period after the watermark during which stragglers still update an already-emitted result. Requires downstream consumers that can handle a correction — which is a product decision, not just a technical one.
Window types
Tumbling (fixed, non-overlapping: "per minute"), sliding (fixed, overlapping: "last 5 minutes, computed every minute"), session (grouped by a gap in activity: "one user's browsing session").
Checkpointing
A consistent snapshot of all operator state, taken by flowing barriers through the dataflow, paired with the source offsets that state corresponds to. On failure, restore and replay from those offsets. This is why replayable sources are a requirement rather than a nicety.
Backpressure
Slowness propagating upstream so a slow sink does not cause unbounded buffering. Monitor lag, not just throughput — throughput can look healthy while you fall further behind every minute.

The design-round framing to carry: batch is a special case of streaming with a very long window. When someone asks you to design a system that computes something over recent events, the real questions are which time you window on, how long you wait for stragglers, where the state lives, and what happens on restart. You know all four answers already.

Chapter seven

The log as the backbone of an architecture

Here is an idea that ties this whole series together, and it will feel natural to you in a way it does not to most people.

An append-only log has now appeared four times in four different disguises: the write-ahead log that gives a database durability, the replication stream that keeps followers in sync, the immutable file that an LSM tree writes, and the Kafka topic your pipelines read. That is not a coincidence. It is the same structure, and it is the most useful primitive in distributed systems, because it is the only one that is simultaneously fast to write, cheap to replicate, and replayable.

Every derived system is a function of the log. Rebuilding one means replaying from the beginning — which is backfill, and it is why this shape is worth so much.

Once you see an architecture this way, several things stop being mysterious:

  • Why is the search index allowed to be stale? Because it is derived. It is a materialized view over the log, and staleness is lag.
  • How do you fix a corrupted downstream system? Delete it and replay. You do this already when a dbt model is wrong.
  • Why does the dual-write problem disappear? Because there is only one write — to the source of truth — and everything else follows from the log.
  • Why is a cache invalidation strategy suddenly easy? Because the log tells you exactly what changed, in order. Consuming a change stream is far more reliable than guessing TTLs.

This is the same shape as your medallion or bronze-silver-gold architecture: one immutable source, many derived views, all rebuildable. You have been doing event-sourced architecture in batch. Saying that in an interview — "I'd treat the search index and the cache as derived views over a change stream rather than as things to write to directly" — reads as a senior instinct.

Chapter eight

Keeping it up when something fails

In batch, a failure means a late table. Online, a failure means a cascade, because everything is calling everything else while under load. These are the standard defences, and each one exists because of a specific way systems die.

1Timeouts on every network call

An unbounded call is a thread leak waiting for traffic. Without a timeout, a slow dependency consumes every thread you own and your service stops serving everything, not just the affected path. Set them deliberately — a timeout longer than your own SLO is a timeout that does nothing.

2Retries with backoff — and jitter

Retry, but wait longer each time. And add randomness, because backoff without jitter synchronizes your clients: they all fail at once, all wait exactly two seconds, and all retry in the same millisecond, producing a wave that keeps the recovering service down. Full jitter — sleep a random duration between zero and the backoff — is the standard fix.

Also: only retry idempotent operations. This is where chapter five earns its keep.
3Circuit breakers

After N consecutive failures, stop calling for T seconds and fail immediately. Counter-intuitive and correct: when a dependency is dying, the kindest thing you can do is stop sending it traffic. It also protects you, since fast failure frees the threads that would otherwise queue up.

4Bulkheads

Separate connection pools and thread pools per dependency, so the failing one cannot starve the healthy ones. Named after ship compartments, for exactly the reason you would guess.

5Load shedding, and graceful degradation

When saturated, reject early at the edge. A fast 503 is far better than a request that queues for thirty seconds holding resources and then times out anyway. And define what the degraded experience is: serve stale cache, drop personalization, return the unranked list. Being able to say what your system looks like at 50% capacity is a product-minded answer that most candidates never give.

The failure mode all of these prevent

Cascading failure. One service slows. Its callers' threads pile up waiting. They slow. Their callers pile up. Within a minute an entire architecture is down because of one unhealthy dependency at the bottom — and it stays down after the original problem is fixed, because every client is now retrying furiously at once. Every mechanism above exists to break one link in that chain, and naming the chain is what makes the mechanisms coherent rather than a checklist.
