How data is stored.

You write SQL every day and you have opinions about Parquet. What you probably have not done is watch a database being built — starting from an empty file, hitting a wall, fixing it, hitting the next wall. That construction is the fastest way to understand every storage decision you will ever make, because each feature exists to solve a specific failure of the version before it. By the end of this book, "should this be Postgres or Cassandra" stops being a preference and becomes a derivation.

Chapter one

Build a database from an empty file

Here is the world's simplest database. Two operations, both correct.

db_v1 — genuinely a database, for about a day
def set(key, value):
    with open("data.db", "a") as f:      # "a" = append
        f.write(f"{key},{value}\n")

def get(key):
    result = None
    with open("data.db") as f:
        for line in f:                     # scan the whole file
            k, v = line.rstrip().split(",", 1)
            if k == key:
                result = v                  # keep going: the LAST one wins
    return result

Do not dismiss it. Writes are as fast as the hardware allows, because appending is sequential — the thing Book 2 said is dramatically faster than random access. It is durable in the sense that data survives a restart. And updates work without any update logic: writing the same key twice leaves both records, and the later one wins on read. That "append a new version instead of modifying the old one" trick is not a hack; it is the foundation of write-ahead logs, LSM trees, Kafka, and your own insert-only fact tables.

Wall one: reads are O(n)

At a million records, every read scans the whole file. The fix is an index: a second structure that tells you where to look. The simplest is a hash map from key to byte offset, held in memory.

db_v2 — add an index
index = {}          # key -> byte offset in the file

def set(key, value):
    with open("data.db", "a") as f:
        offset = f.tell()                   # where this record starts
        f.write(f"{key},{value}\n")
    index[key] = offset                     # remember it

def get(key):
    if key not in index: return None
    with open("data.db") as f:
        f.seek(index[key])                  # jump straight there: O(1)
        return f.readline().rstrip().split(",", 1)[1]

Reads are now one disk seek. And notice what the index cost you — this is the general shape of the trade, and it never changes:

  • Writes got slower, because every write now updates two things.
  • Memory is now a constraint: the index must fit in RAM.
  • Range queries got no faster. A hash index can find one key. "All keys between A and F" still means scanning everything, because a hash deliberately destroys ordering.

That last point is why real databases use sorted structures instead of hash maps, and it is the single most important consequence in this chapter.

Wall two: the file grows forever

Every update appends. A key written a thousand times occupies a thousand records, 999 of them dead. The fix is compaction: periodically rewrite the file keeping only the latest version of each key.

You know this problem. It is the small-files problem, and compaction is the job you already run. Cassandra and RocksDB run exactly this loop internally, for exactly this reason.

Wall three: a crash mid-write

If the process dies halfway through appending, the last record is a torn half-line, and your in-memory index is gone entirely. Real databases fix this with a write-ahead log: before applying any change, write your intent to a log and fsync it to durable storage. On restart, replay the log and you are consistent again.

Two things follow. First, this is what the D in ACID actually costs: a commit cannot return until the log physically reaches the disk, which is why commit latency has a hard floor and why disabling synchronous commit makes a database dramatically faster and slightly dishonest. Second, this is precisely your streaming checkpoint — snapshot plus replay-from-offset — and the two mechanisms are the same idea.

Wall four: the index no longer fits in memory

A billion keys will not fit in a hash map. So the index has to live on disk, which means it must be structured so that finding a key takes very few disk reads. That structure is a B-tree, and it is the next chapter.

What you just built

An append-only log with an index, periodic compaction, and a write-ahead log for durability. That is not a toy — it is a fair description of how a modern key-value store works, and every step was forced by a specific failure of the step before. Whenever a storage feature seems arbitrary, ask which wall it was built to solve.

Chapter two

What an index really is

A table without an index is an unordered pile of rows; finding WHERE email = 'x' means reading every one. An index is a separate structure, kept sorted, mapping column values to row locations. In nearly every relational database that structure is a B+ tree.

The shape, and why it is only four levels deep

Data lives on disk in fixed-size pages, typically 8 KB. A B+ tree stores keys in those pages with a very high branching factor: an internal page holds hundreds of keys and pointers. So the tree over a billion rows is about four levels deep — root, two internal levels, leaf.

Four page reads to find any row among a billion. The linked leaves are why BETWEEN and ORDER BY on an indexed column are cheap — you descend once and then walk sideways.

Two structural facts do all the work. High fan-out keeps the tree shallow, so lookups are a handful of reads rather than thousands. Linked leaves mean the index serves range scans as well as point lookups — which is exactly what a hash index cannot do, and why B-trees won.

The rules that fall out of the structure

Indexes slow writes
Every insert, update and delete must maintain every affected index. Five indexes means roughly six writes per write. "Just add an index" is never free, and on a write-heavy table it can be the problem rather than the fix.
Left-prefix only
An index on (user_id, created_at) serves WHERE user_id = ? and WHERE user_id = ? AND created_at > ? — but not WHERE created_at > ? alone, because the tree is sorted by user_id first. Column order is a design decision, and getting it wrong is the most common index mistake there is. It is the same logic as your partition-column ordering.
Covering indexes
If the index contains every column the query needs, the database never follows the pointer to the row at all. Often a 10× win. This is column pruning, applied to an index.
Low cardinality barely helps
An index on a boolean over 100M rows still points at 50M of them. The planner will correctly ignore it and scan — and it is right to, because 50 million random reads are slower than one sequential pass.
Functions disable it
WHERE LOWER(email) = 'x' cannot use an index on email; you need an index on the expression. Same reason a transformation defeats partition pruning in your world.
Clustered vs secondary
In MySQL's InnoDB the table is the primary-key B-tree, so a secondary index stores the primary key and every secondary lookup pays a second descent. This is why a random UUID primary key hurts there — inserts land all over the tree instead of appending at the end.

How the planner joins

Three algorithms, and you have used all three by hand in Spark:

AlgorithmHowYour equivalent
Nested loopFor each row of A, look up matches in B via an indexA broadcast join where the lookup side is indexed. Catastrophic without the index — that is O(n×m).
Hash joinBuild a hash table on the smaller side, probe with the largerSpark's shuffle hash join. Needs memory; spills when it doesn't fit — the same spill you have watched.
Merge joinSort both sides, then walk them in lockstepSort-merge join. Free when both inputs are already sorted on the key.

Read the plan rather than guessing. EXPLAIN ANALYZE shows the chosen algorithm, estimated versus actual row counts, and time per node. The tell for a bad plan is a large gap between estimate and actual — stale statistics led the planner to choose a nested loop for what turned out to be ten million rows. You already read Spark UI stage details this way; it is the same skill.

Chapter three

Two engine families, and the trade between them

Chapter one built an append-only log with compaction. Chapter two built a sorted tree updated in place. Those are the two families, and essentially every storage system is one or the other.

B-tree — update in place
LSM tree — append and merge
Postgres, MySQL/InnoDB, most relational databases

Cassandra, RocksDB, HBase, ScyllaDB — and, structurally, your lakehouse
Write: find the leaf page, modify it in place, journal first to the WAL. Random I/O.

Write: append to an in-memory table; when it fills, flush it to disk as an immutable sorted file. Purely sequential.
Read: descend the tree. One place to look.

Read: check the memtable, then each level of sorted files, newest first. Several places to look — Bloom filters skip most of them.
Costs: random writes; pages sit 50–70% full, so space is wasted.

Costs: read amplification, and 10–30× write amplification from compaction rewriting the same data repeatedly. Compaction pauses show up as p99 spikes.
Wins: predictable reads, mature transactions, secondary indexes, read-modify-write.

Wins: enormous write throughput, dense packing, and cheap sequential ingest.

The general statement of the trade is the RUM conjecture: you get to optimize two of Read cost, Update cost, and Memory (space) overhead, never all three. B-trees choose read and space; LSM trees choose update and space; a pure in-memory index chooses read and update.

You have been running an LSM tree by hand

Write immutable files. Never modify them. Reads must consider several files and take the newest version of each key. Periodically merge small files into larger ones to keep reads fast. That is an LSM tree, and it is also a description of an Iceberg or Delta table with its compaction job. The reason your lakehouse looks like this is the same reason Cassandra does: object storage and distributed filesystems make sequential writes cheap and in-place updates impossible.

Bloom filters, since they only exist to make this work

An LSM read might have to check twenty files. Checking each one is a disk read, and most will not contain the key. A Bloom filter is a small bit array plus a few hash functions that answers "definitely not here" or "maybe here" in constant time, with no false negatives. Attach one per file and you skip almost every unnecessary read.

The sizing rule is worth memorizing because it comes up constantly: about 10 bits per element gives a 1% false-positive rate — so a billion keys costs roughly 1.2 GB. And the follow-up you will always be asked: you cannot delete from a standard Bloom filter, because clearing bits would break other elements. The answers are a counting Bloom filter, a cuckoo filter, or rebuild-and-swap.

Chapter four

Rows, columns, and why your warehouse is a different animal

This is the chapter where your existing knowledge is the advantage rather than the gap — most backend engineers understand this far less well than you do. The point here is to make the contrast explicit, because in a design interview you will be expected to know when to reach for each.

A row store keeps all of a row's columns together on a page. Fetching one complete record is one read. A column store keeps each column's values together. Fetching one column across a billion rows reads only that column's bytes.

Row store (OLTP)Column store (OLAP)
Query shape"Give me everything about user 12345" — few rows, all columns"Average revenue by region for last quarter" — billions of rows, four columns
Write shapeSingle-row inserts and updates, constantly, concurrentlyBulk append; updates rare or forbidden
CompressionPoor — adjacent bytes are unrelated typesExcellent — a column holds one type with repeated values, so run-length and dictionary encoding win enormously. Often 10× or more.
Latency targetSingle-digit millisecondsSeconds to minutes, and nobody minds
ConcurrencyThousands of concurrent small transactionsA few dozen large queries
ExamplesPostgres, MySQL, DynamoDBBigQuery, Snowflake, ClickHouse, Parquet on object storage

The rule to carry into a design round: the transactional store is the source of truth and serves the product; the analytical store is derived and serves questions. They are not competitors and you will almost always have both. Where candidates go wrong is proposing an analytical store for a serving path — "we'll query Snowflake for the user's profile" — which fails on latency and concurrency, or proposing per-row updates against a columnar store, which fails structurally.

The bridge between them is worth naming because it comes up in nearly every data-platform design: change data capture. Rather than querying the production database on a schedule (which loads it and misses intermediate states), you read its write-ahead log — the same log from chapter one — and stream every change into the analytical side. That is Debezium, and it is the reason the WAL turns out to be a public interface rather than an implementation detail.

Chapter five

Transactions, and what isolation actually buys

ACID gets recited more than understood. Here is what each letter costs and provides.

Atomicity
All the statements, or none of them. Implemented with the write-ahead log: changes are journalled before being applied, so a crash mid-transaction can be rolled back. It means "all or nothing", not "instantaneous".
Consistency
The weakest and most misunderstood letter. It means only that declared constraints — foreign keys, uniqueness, checks — hold before and after. It is not the "C" in CAP, which is a completely different property. If someone conflates them, that is a tell.
Isolation
Concurrent transactions do not see each other's partial work — to whatever degree the isolation level promises. This is where all the real complexity lives.
Durability
Once committed, it survives a crash — which requires an fsync and therefore has a latency floor.

MVCC — which you already use

How can one transaction read a table while another is rewriting it, without either blocking? Multi-version concurrency control: writers create new versions of rows rather than overwriting, and each transaction sees a consistent snapshot as of the moment it started. Readers never block writers; writers never block readers.

Iceberg and Delta do exactly this on your tables — a write creates a new snapshot, readers keep reading the old one until it commits, and time travel is simply reading an older snapshot deliberately. So you already have the mental model; Postgres just calls the leftovers "dead tuples" and needs VACUUM to reclaim them. And here is the operational consequence worth knowing: a long-running transaction holds back that cleanup for the entire database, which is a very common cause of "why did our disk fill up?"

The isolation levels, and the anomaly each one stops

LevelDirty readNon-repeatable readPhantomWrite skew
Read uncommittedpossiblepossiblepossiblepossible
Read committed (Postgres default)nopossiblepossiblepossible
Repeatable read (MySQL default)nonomostlypossible
Serializablenononono

In plain terms: a dirty read sees uncommitted data. A non-repeatable read reads the same row twice in one transaction and gets different values. A phantom re-runs the same WHERE and finds new rows.

Write skew is the subtle one and the one worth being able to explain. Two transactions each read a set of rows, each check a condition that currently holds, and each write — and the combination violates the condition, though neither did alone. The canonical example: two doctors are on call, each opens the app, each sees that the other is still on call, and each cancels their own shift. Both transactions were individually valid. Nobody is on call. Only serializable isolation prevents it, and having that example ready is worth real credit.

When the data spans two systems

ACID stops at one database. Beyond it you have three options and no good ones:

  • Two-phase commit — a coordinator asks everyone to prepare, then to commit. Correct, and it blocks: if the coordinator dies after prepare, every participant holds locks indefinitely. Rare in modern systems for exactly that reason.
  • Saga — a sequence of local transactions, each with a compensating action. Book the flight, book the hotel; if the hotel fails, cancel the flight. No isolation, so an intermediate state is visible, which the business usually tolerates once it is named.
  • Make it one transaction — frequently the right answer is that the two things belonged in the same service and the same database, and splitting them was the mistake.
Chapter six

Replication: more than one copy

You replicate for three different reasons and they pull in different directions: durability (a machine dies and you still have the data), read capacity (spread reads over copies), and latency (put a copy near the user).

The core mechanism is the same one you have already met twice: ship the log. The leader writes to its write-ahead log, followers receive that log and apply it, and they converge. Everything else is a policy question about timing.

ArrangementGuaranteeUse when
Single leader, async followersFollowers lag by milliseconds to seconds. A failover can lose the last few writes.The default, and it is fine for most things. Reads go to followers, writes to the leader.
Single leader, one sync followerNo data loss on failoverMoney. You pay a full round trip on every write.
Multi-leaderLocal writes in each region, and conflicts are now realMulti-region write locality. You must define conflict resolution — last-write-wins silently loses data; CRDTs don't.
Leaderless quorumTunable per query: if reads + writes > replicas, they overlapDynamo-style stores. N=3, W=2, R=2 is the classic setting.

The bug that replication lag causes, and its fix

A user posts a comment, the write goes to the leader, the page reloads, the read goes to a follower that has not caught up — and their comment is gone. They post it again. Now there are two.

This is read-your-own-writes, the most commonly needed consistency guarantee in ordinary products, and the fixes are mundane: route a user's reads to the leader for a few seconds after they write, or track the write's log position and have the follower wait until it has caught up to it. The lesson generalizes — most consistency requirements are narrow and specific, and the design work is naming which one you need rather than asking for the strongest available.

CAP and PACELC, said correctly

CAP uses its words in a specific technical sense: consistency means linearizability (every read sees the most recent completed write, as though there were one copy), and availability means every non-failing node returns a non-error response. With those definitions: during a network partition, you must choose one. That is all it says — it is silent about the 99.9% of time when there is no partition.

The more useful formulation is PACELC: if Partitioned, choose Availability or Consistency; Else, choose Latency or Consistency. That second clause is the one that governs your daily life, because consistency costs a round trip even when everything is healthy.

And a precision worth having: the consistency guarantees are not a single ladder. Eventual consistency is the floor; above it sit four session guarantees — read-your-writes, monotonic reads, monotonic writes, writes-follow-reads — which are mutually incomparable, none implying another. Above those: causal, then sequential, then linearizable. Transaction isolation is a separate axis entirely.

Chapter seven

Sharding: when one machine is not enough

Replication gives every machine all the data. Sharding gives each machine a slice. You shard when data volume or write throughput exceeds one machine — and not before, because sharding costs you transactions, joins, and simplicity.

You already know the whole of this chapter under the word partitioning. The entire question is the key.

Key choiceGives youCosts you
Hash of entity idEven distribution, no hotspotsRange scans become scatter-gather across every shard
Range (e.g. by time)Beautiful range scans, easy archival of old shardsThe newest shard takes 100% of writes — the hotspot you have already lived
Composite (tenant, time)Locality within a tenant, spread across tenants. Usually right for multi-tenant systems.A single enormous tenant is still a hot shard
GeographyLatency and data residencyCross-region queries become expensive and slow

Rebalancing, and why hash % N is a trap

Send key k to shard hash(k) % N. Now add a machine: N changes, and nearly every key maps somewhere new. You have to move almost all the data to add 10% capacity.

Consistent hashing fixes this: place shards and keys on a ring, and each key belongs to the next shard clockwise. Adding a shard only moves the keys between it and its predecessor — K/N keys instead of all of them. Virtual nodes (each physical machine appearing at many ring positions) even out the distribution. The simpler alternative worth knowing is rendezvous hashing: compute hash(key, shard) for every shard and take the highest — same movement property, no ring to manage, O(N) per lookup.

What sharding takes away

Be honest about this in a design, because it is where the follow-ups go. Cross-shard transactions are gone or extremely expensive. Joins across shards require fetching from several and joining in the application. Unique constraints across the whole dataset need a separate coordination mechanism. Secondary indexes become their own design problem — either local per shard (fast to write, scatter-gather to read) or global (fast to read, and now a distributed transaction to keep in sync).

Which is why the honest first answer to "should we shard?" is usually "not yet — first check whether a bigger machine, a read replica, or a better index solves it." A single modern Postgres handles tens of thousands of writes per second and terabytes of data. That is a lot of product.

Chapter eight

Choosing a store, as a derivation

Now the choice is mechanical. Ask four questions in order, and the answer falls out.

  1. What are the access patterns?

    Point lookups by key? Range scans? Full-text relevance? Multi-hop traversal? Aggregations over billions of rows? Similarity over vectors? Each one favours a different structure, and access patterns are the input to the decision, never an afterthought.

  2. How much data, and how many writes per second?

    Under a terabyte and tens of thousands of writes per second, one relational database does it and everything else is premature.

  3. What consistency does the product actually need?

    Name the weakest guarantee that works. "Likes can be eventually consistent; the user must read their own comment immediately; the account balance needs serializable" is three different answers in one system, and that is normal.

  4. What is the cost of being wrong?

    Losing a view count is fine. Losing money is not. This is what decides synchronous versus asynchronous replication, and whether you pay for stronger isolation.

If the answer is…Reach forBecause
"I don't fully know the access patterns yet"RelationalIt is the only family that serves queries you did not plan for. This is the correct default and the honest answer surprisingly often.

The operational detail that shows experience

Schema changes without downtime. Adding a nullable column is instant. Adding a NOT NULL column with a default may rewrite and lock the whole table. The safe pattern is expand then contract: add the new column, write to both old and new, backfill in batches, switch reads, then drop the old one — four deploys instead of one, and no outage. You do the same dance when you evolve a table schema without breaking downstream consumers; it is the same problem, and mentioning it unprompted signals that you have shipped something.
