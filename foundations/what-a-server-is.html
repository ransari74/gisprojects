What a server actually is.

You can design distributed systems without knowing what happens inside one machine — badly. Almost every "why is this slow" and "how many of these do I need" question bottoms out in four physical facts about hardware, and once you hold those, capacity estimation stops being guesswork and becomes arithmetic. This is the shortest book in the series and the one everything else stands on.

~30 min readAssumes Book 1Mostly numbers
Chapter one

The machine, drawn to scale

A server is four things: a CPU that computes, memory that holds what it is computing on, disk that remembers when the power goes out, and a network card that talks to other machines. Everything else is detail. What matters is that these four operate at wildly different speeds, and the differences are so large that they are hard to feel.

So here they are stretched into human time. Pretend one CPU cycle takes one second instead of a third of a nanosecond:

OperationReal timeIf a cycle were 1 second
One CPU cycle0.3 ns1 second
L1 cache hit~1 ns3 seconds
L2 cache hit~4 ns13 seconds
Main memory read~100 ns5 minutes
NVMe SSD read (4 KB)~100 µs4 days
Round trip inside a datacenter~0.5 ms3 weeks
Spinning disk seek~10 ms1 year
Round trip across a continent~70 ms7 years
Round trip around the world~200 ms21 years

Read the bold rows together. If reading a value from memory takes the CPU five minutes of subjective time, then asking another service for that value takes three weeks, and asking a service on another continent takes seven years. That is the entire reason distributed systems are designed the way they are. Every architectural pattern you will learn — caching, replication, denormalization, CDNs, batching, asynchronous processing — exists to avoid one of the bottom four rows.

The one you already know

This is the same insight as "avoid the shuffle." A shuffle is expensive for exactly this reason: it converts local memory access into network transfer, at the scale of an entire dataset. Your existing instinct to restructure a job so data stays local is the instinct that makes a good systems engineer — you have just been applying it to gigabytes rather than to milliseconds.

The four numbers to memorize

Not the whole table. Four:

  • Memory: 100 nanoseconds. Effectively free. If it is in RAM, stop worrying about it.
  • SSD: 100 microseconds. A thousand times slower than memory. Still fast, and modern NVMe sustains 500,000+ operations per second when you keep many requests in flight at once — latency and throughput are different questions.
  • Same-datacenter network: 0.5 milliseconds. Your service-to-service tax. Ten sequential hops means a 5 ms floor before anyone does any work. This is why deep call chains are a latency problem regardless of how fast each service is.
  • Cross-country network: 70 milliseconds. Physics — light in fibre, plus routing. You cannot engineer around it; you can only avoid crossing, which is what a CDN and a regional replica are for.

And two more about size

A modern server has roughly 64 to 512 GB of RAM and 1 to 10 TB of local SSD. Those two numbers answer more design questions than any other pair, because the first question in most designs is does the working set fit in memory on one machine? If yes, the design is simple. If no, everything downstream — sharding, caching tiers, cold storage — follows from that single "no."

You will also want row-size arithmetic: an integer is 4 bytes, a timestamp 8, a UUID 16, a character 1. Add about 20% for row and index overhead. A 768-dimension float32 embedding is 3 KB — a number that decides whether a vector index fits in RAM.

Chapter two

Where a request's 200 milliseconds go

Abstract numbers become useful when you spend them. Here is a realistic budget for one API call that loads a user's dashboard — and note how little of it is your code.

StepCostWhat is happening
DNS lookup0–50 msUsually cached to zero. Cold, it can be surprisingly expensive.
TCP handshake1 round tripFree if the connection is reused. This is why connection pooling matters so much.
TLS handshake1 round tripAlso free on reuse. On a cold cross-country connection these two alone are ~140 ms.
User → edge10–70 msPhysics. Only a CDN or a regional deployment reduces it.
Load balancer → service~0.5 msOne datacenter hop.
Service → cache (hit)~1 msA network hop plus a sub-millisecond lookup.
Service → database (indexed read)1–10 msNetwork hop, plus index descent, plus reading pages that are hopefully in the database's memory.
Database read that misses memory10–100 msNow you are paying for disk, possibly several times. This is the cliff.
Your actual code0.1–5 msSerialization, business logic, JSON encoding. Usually a rounding error.
The lesson, and it is the whole chapter

Almost all of a request's time is spent waiting on something else. Your code is rarely the bottleneck; the calls your code makes are. This is why optimizing an algorithm from O(n log n) to O(n) inside a request handler usually changes nothing measurable, while removing one database round trip changes everything. It is also why "how many network calls does this make?" is the most useful question you can ask about a proposed design.

Two consequences worth internalizing

Sequential calls add; parallel calls take the max. If your handler makes five calls of 10 ms each in sequence, that is 50 ms. Made concurrently, it is ~10 ms. The single most common easy win in a slow service is noticing that four of its five dependencies do not depend on each other. This is your DAG instinct again — Airflow parallelizes independent tasks for exactly this reason.

The N+1 problem is the same mistake at a different scale. Fetch 100 rows, then loop and fetch a related record for each one: 101 round trips instead of 2. In a pipeline you would never do this — you would join. In application code it happens constantly, because the loop looks innocent. Whenever you see a network call inside a loop, that is the bug.

Chapter three

Memory, the page cache, and why systems fall off cliffs

You have already met this chapter's content, in the form of tuning executor memory and watching a job spill to disk. The mechanics are the same; only the words change.

Virtual memory, briefly

Every process sees its own private address space. The operating system maps those addresses to real physical memory in fixed-size pages (usually 4 KB). This is why one process cannot read another's memory, and why memory can be over-committed — the OS hands out addresses freely and only backs them with physical pages when actually touched.

The page cache — the most important thing you didn't know had a name

When a program reads a file, the OS keeps a copy of those pages in otherwise-unused RAM. The next read of the same file does not touch the disk at all. This is the page cache, and it is why "reading from disk" is frequently not reading from disk.

Two consequences that explain a great deal of production behaviour:

  • A database appears fast until its working set exceeds memory, and then it collapses. Not gradually — sharply. While the hot pages fit, nearly every read is a memory read at 100 ns. Once they do not, reads start hitting the SSD at 100 µs, a thousand times slower, and queue depth explodes. If you ever hear "it was fine for a year and then degraded over a weekend," suspect this.
  • Free memory is not wasted memory. A server showing 2 GB free and 200 GB "used by cache" is healthy — the OS is doing its job. Alarming at that number and shrinking the machine is a classic mistake.

Sequential beats random, at every level

Reading 1 MB sequentially from an SSD takes about 200 µs. Reading 256 random 4 KB blocks — the same megabyte — takes far longer, because each one pays full latency. The same asymmetry exists in memory (the CPU prefetches ahead) and in your world (a full scan of a Parquet file is dramatically faster than 10,000 point lookups).

This asymmetry is the reason for several designs you will meet in Book 3: why append-only structures are fast to write, why databases store rows in sorted pages, why columnar formats exist, and why a query planner will sometimes deliberately choose to scan an entire table rather than use an index — because at some point, 30% of a table read sequentially beats 30% of it read randomly.

Garbage collection, and why it shows up as p99

In a garbage-collected runtime — Java, Go, Python, whatever the service is written in — the runtime periodically pauses to reclaim memory. In Spark you have felt this as a task that inexplicably took much longer than its peers. In a service it appears as tail latency: the median request is 20 ms and the 99th percentile is 400 ms, because one request in a hundred was unlucky enough to be in flight during a pause. This is one of the most common reasons a p99 looks nothing like a p50, and knowing to suspect it makes you look experienced.

Chapter four

Processes, threads, and event loops

A server has to handle many requests at once. There are three ways to arrange that, and the choice has architectural consequences.

The distinction that governs everything: concurrency vs parallelism

Parallelism is doing several things at the same instant — which requires several CPU cores. Concurrency is having several things in progress at once, most of which are waiting. A single core can be concurrent with ten thousand things if 9,999 of them are blocked on the network.

From this falls the most useful classification in server design:

  • I/O-bound work wants concurrency. Your handler spends 95% of its time waiting on a database. You need many requests in flight, not many cores.
  • CPU-bound work wants parallelism. Your handler is parsing, compressing, or running a model. You need cores, and no amount of concurrency helps.

Confusing the two produces both classic mistakes: an async web server that pins a core doing JSON parsing and stalls every other request, and a thread pool sized to the core count that spends its entire life idle, waiting on a database.

The three models

ModelHow it worksWhere it wins / breaks
Process per requestFull isolation, separate memoryBulletproof and heavy. Mostly historical for web serving, though it is exactly what a Spark executor is — and its isolation is why one failing task cannot corrupt another.
Thread per requestThreads share memory within one process; a blocking call parks the thread until it returnsSimple to write — blocking code reads sequentially. Breaks at high connection counts, because each thread costs memory and the OS spends its time context-switching between them.
Event loopOne thread asks the kernel "which of these 10,000 sockets is ready?", handles those, and goes back to waitingEnormous numbers of mostly-idle connections on one thread. Breaks catastrophically if any handler blocks — one slow function stalls the entire process.

Modern runtimes mostly blend these: green threads or coroutines (Go's goroutines, Java's virtual threads, Python's asyncio) let you write blocking-looking code that runs on an event loop underneath. You get the readability of threads with the scaling of an event loop, and pay in harder debugging and profiling.

Why this matters for a design, concretely

"How many concurrent connections can one machine hold?" is a real design question — it decides how many machines a chat or streaming system needs. The rough answer is tens of thousands of idle connections per node on an event-loop model. So 100 million concurrent users needs on the order of 2,000 machines just to hold the sockets, before any of them do work. That number then raises the next question — how does a message find the one machine in two thousand holding a given user's connection? — which is the connection-registry problem, and it is the piece people forget.

The context switch, and why it caps you

Swapping one thread off a core for another costs on the order of a microsecond, plus the cache pollution afterward — which often costs more than the switch itself. A microsecond sounds like nothing until you have 10,000 threads all becoming runnable, at which point the machine spends its time switching rather than working, and throughput falls as you add load. That non-monotonic behaviour — more load producing less work — is one of the nastier failure modes in serving, and it is why bounded thread pools and load shedding exist.

Chapter five

The genuinely new part: several things touching the same state

This chapter contains the one topic with no equivalent in your batch experience, because a framework was protecting you from it. In Spark, two tasks never modify the same variable — they work on separate partitions in separate processes, and the framework merges results. In a service, a thousand requests can touch the same row in the same millisecond and nothing is refereeing.

The race condition

Consider incrementing a counter:

Three operations, not one
views = read(key)      # thread A reads 100 ... thread B also reads 100
views = views + 1      # A computes 101   ... B computes 101
write(key, views)      # A writes 101     ... B writes 101

# Two views were recorded. The counter says 101. One update vanished,
# silently, with no error anywhere. This is a LOST UPDATE, and it is the
# root of most concurrency bugs.

Nothing crashed. No exception was raised. The data is simply wrong, and it will be wrong more often the more traffic you get — which means it works perfectly in testing and fails in production. That property, correctness that degrades with load, is what makes concurrency bugs feel qualitatively different from the bugs you are used to.

The five ways out, from cheapest to most expensive

Don't share
The best answer where available. If each request touches its own data, there is no race. Partitioning work by key — routing all requests for a given user to the same handler — turns a concurrency problem into a routing problem. This is exactly what partitioning a DataFrame does for you.
Immutability
If nothing is ever modified, nothing needs coordinating. Append a row rather than update one; compute the total by summing. This is why event logs and append-only stores are so common — and it is the same reason your warehouse prefers insert-only fact tables over mutable ones.
Atomic operations
Ask the storage layer to do read-modify-write as one indivisible step: INCR in Redis, UPDATE t SET n = n + 1 in SQL. Correct, fast, and the right answer for counters. The limitation is that it only covers operations the store supports natively.
Optimistic concurrency
Don't lock. Read a version number, and on write assert it hasn't changed — UPDATE … WHERE version = 7 — retrying if the update affects zero rows. Ideal when conflicts are rare, which they usually are. Iceberg and Delta do exactly this on your tables.
Pessimistic locking
SELECT … FOR UPDATE: take the lock first, make others wait. Correct under heavy contention, and it caps your throughput at one holder at a time, plus it introduces the possibility of deadlock — A holds lock 1 and wants 2 while B holds 2 and wants 1. The practical defence is a global lock ordering: always acquire in the same order.

Notice the shape of that list: the good answers avoid the problem and the expensive answers manage it. That ordering is worth carrying into design work generally — when a design needs a distributed lock, the first question is whether it could be restructured so it doesn't.

Chapter six

What this buys you in a design

Four concrete moves you can now make that you could not before this book.

1Sizing a fleet

"One commodity app server handles roughly 1,000–10,000 requests per second, depending on how much work each does." So 300,000 requests per second at peak needs on the order of 30–300 machines, and you should say which end you expect and why — "each request makes three database calls, so I'd assume the low end and load-test it". Naming a number and its uncertainty beats naming no number.

2Locating a bottleneck before writing code

Add up the round trips in your proposed request path. If a design makes eight sequential service calls, it has a 4 ms floor before doing anything, and a p99 that will be dreadful because it inherits the tail of eight dependencies. Say so, and fan them out.

3Answering "does it fit in memory?"

The most decisive question in most designs. 50 million cached objects at 500 bytes each is 25 GB — one machine, easily. The same 50 million objects at 200 KB each is 10 TB — an entirely different architecture. The arithmetic takes ten seconds and changes the answer completely.

4Explaining a p99 that doesn't match the p50

The causes are a short list, and now you know all of them: garbage collection pauses, a cache miss falling through to disk, queueing behind a saturated thread pool, a retry after a timeout, or one slow dependency in a fan-out where you wait for the slowest. Being able to enumerate that list on demand is a strong signal of having actually run something.

Tail latency is where the interesting engineering is, and it is where most candidates have nothing to say.
